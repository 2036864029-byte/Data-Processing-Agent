## 一、产品概述

### 1.1 产品定位

本产品是一款**面向海量异构文档 / 数据批量处理场景的 Agent 产品**，采用"控制面 / 数据面分离 + 插件化能力"架构，实现多格式数据从接入、嗅探、路由、解析、质检、修复到输出的全流程自动化。

**产品的一句话定位：**

> 用最划算的算力，把 80% 的常规数据做对；把剩下 20% 的复杂数据**准确识别并标记出来**，交给高成本链路或人。

**产品不是：**

- 不是"最强 PDF 解析器"（不争 20% 高精尖场景的解析精度冠军）
- 不是通用 RPA / 工作流引擎
- 不是标注平台
- 不是"每一步都调大模型"的伪 Agent

### 1.2 要解决的核心问题

| #  | 问题         | 现状痛点                      | 本产品的解法                       |
| -- | ---------- | ------------------------- | ---------------------------- |
| P1 | 格式异构，工具割裂  | CSV/TXT/PDF/图片各用各的工具，人工切换 | 统一接入 + 两级路由 + 插件注册表          |
| P2 | 全量 OCR 成本高 | 80% 的简单数据也走重链路，算力浪费       | 逐页置信度路由，简单页走 CPU 原生抽取        |
| P3 | 个性化需求改动难   | 改规则要改代码，影响稳定性             | 声明式 RulePack，用户只改数据不改代码      |
| P4 | 失败无闭环      | 简单重试无效，缺少归因与分级处理          | 页面画像 + 分级兜底 T0–T3 + 预算 + 诊断卡 |
| P5 | 质量不可证明     | 没有人说得清"还原度"是多少            | 四层质检 + 往返校验 + 黄金集标定          |
| P6 | 扩容困难       | 单机瓶颈，无法横向扩展               | 数据面无状态 worker + 队列 + 幂等键     |


### 1.3 产品目标

| 目标 | 指标                                | 定义与测量                                           |
| -- | --------------------------------- | ----------------------------------------------- |
| 效率 | 常规数据处理吞吐 ≥ **30 万页/日/节点**（16C64G） | 前提：简单页占比 ≥ 80%，端到端 ≤ **150ms/页**；压测取连续 1 小时稳定吞吐 |
| 成本 | 加权单页成本 ≤ 全量 OCR 方案的 **10%**       | 按"简单:中等:复杂 = 8:1.5:0.5"加权；见 9.4                 |
| 质量 | STP 率 ≥ 80%，误放率 ≤ 2%              | STP = 一次通过文档数 / 总文档数；误放率见 6.2                   |
| 灵活 | 新增业务规则零代码、无需重启                    | 新增 RulePack 到生效 ≤ 5 分钟                          |
| 扩展 | 新增节点吞吐提升 ≥ 70%                    | 10 节点集群，文档级分片，控制面不成为瓶颈                          |
| 部署 | 完全离线私有化，数据不出域                     | 断网环境全链路跑通                                       |

### 1.4 核心产品原则

1. **二八原则，性能优先**：优先保障绝大多数常规数据的处理效率，复杂场景单独分级处理，不因为少数场景拉低整体性能。
2. **通用与个性分离**：通用处理能力保持标准统一；所有业务个性化通过**配置层（数据）**&#x5B9E;现，不侵入核心处理能力。
3. **闭环可控，边界清晰**：所有异常处理有明确策略、有终止条件；**重试必须改变变量**，禁止无信息增益的重复执行。
4. **能力插件化，可插拔可替换**：各类处理能力以插件形式存在，遵循统一契约（见 5.1），可新增、可替换、可升级。
5. **裁判不干活，干活的不裁判**：质检与解析分离，保证质量判定可复现、可评测。
6. **数据做约束，模型做判定，代码做执行**：变更面收敛到数据层，代码层保持只读。
7. **固定成本摊薄**：解析库的主要成本在"打开文件、解析页树、建字体缓存"，不在"抽这一页"。所有涉及文件级固定开销的操作必须**批量化**，禁止按页重复支付。
8. **长任务可续跑**：任何可能超过 10 分钟的任务，必须能在任意时刻被强杀并从断点继续，已完成的批不得重做。worker 是无状态的，状态只在库里。
9. **一套代码，单机多机同构**：不存在"单机版"与"集群版"两套代码；差别只在后端实例的地址。这条决定了三年后能否平滑扩容。
10. **先判定，再增强，最后才换引擎**：成本阶梯必须从低到高走，跳级使用昂贵手段等于放弃成本优势。

### 1.5 能力边界（明确不做什么）

| 边界             | 说明                                                   |
| -------------- | ---------------------------------------------------- |
| 不承诺最难的 20%     | 对复杂页只承诺"100% 识别并标记 + 给出诊断"，不承诺自动修复成功                 |
| 不做通用 RPA       | 不模拟鼠标键盘、不做跨系统流程编排                                    |
| 不做标注平台         | 人工标注仅作为黄金集建设与升级兜底                                    |
| 不做模型训练平台       | 小模型只做推理与蒸馏部署，不做在线训练                                  |
| 不开放任意代码执行      | 用户侧只允许声明式规则；扩展能力走沙箱插件（见 4.6.4）                       |
| P0/P1 不做图形界面   | 只交付 API + CLI + 结果文件 + 报告；UI 统一归 P2（见 8.3）           |
| **不做内部插件网关**   | 热路径插件同进程直接调用；跨进程调用面只给冷路径（见 5.5）。MCP 只做对外出口，不做内部调用协议  |
| **不做"单机精简版"**  | 一旦出现第二套代码路径，多机版即成为无人测试的分支（见 4.8.8、R11）               |
| **不做无位置信息的修复** | 没有 `location` 的缺陷不进入修复队列，只能统计。整页重做对确定性函数无意义（见 4.5.7） |

## 二、Agent 能力边界（核心章节）

> 本章定义 Agent 到底在哪里、做什么、不做什么。**研发、测试、验收均以本章为准。**

### 2.1 四角色模型

| 角色                  | 性质          | 职责                               | 部署形态                 | 明确禁止           |
| ------------------- | ----------- | -------------------------------- | -------------------- | -------------- |
| **主控（任务编译器 + 调度器）** | 有状态、低频决策    | 意图 → Plan / TaskSpec；排任务；管预算；决定升级       | 同进程：编译器（模型）+ 调度器（代码） | 不解析、不评分、不碰文档内容 |
| **解析执行器（Worker）**   | 无状态、确定性、可并行 | 解析一页 / 一批页 / 一个文件，产出不可变 artifact | 独立**进程**（非独立服务）      | 不自判合格、不自行重试    |
| **质检器（QC）**         | 只读、事件驱动     | 读指标 → 判 pass/fail → 归因 → 建议动作    | 同进程库 + 可外置           | **不重新解析、不改产物** |
| **修复执行器（Repairer）** | 写候选、事件驱动    | 执行修复动作，产出候选 artifact             | 同进程算子库               | 不给自己打分         |

**铁律：裁判不干活，干活的不裁判。**

**关于角色命名的两点澄清（防止被实现成三个服务）**

1. **四个角色是职责，不是四个部署单元。** 除了解析器需要独立进程（因为 Rust 扩展崩溃会杀掉整个进程，见 4.8.5），其余三者都在同一个控制进程内，是模块边界而非网络边界。
2. **"Agent"这个词只应出现在任务级三处模型调用点上**（2.2）。把质检器叫 Agent、把修复器叫 Agent，会让团队去建三套服务、三套重试、三套监控、三套部署——而它们本来只是三个类。

> **面试/评审时的标准说法**：本产品没有做多智能体。它是一条确定性流水线，在任务级三个点上使用了模型（意图→Plan、偏离重规划、整本策略切换）。做了**职责**分离：解析、质检、修复。质检必须独立的理由是业务性的——产品的核心承诺是 STP 率（一次通过率），如果解析模块自己报告质量，这个指标就是自评，客户不认。

### 2.2 Agent 只在三处出现

| 位置                | 输入            | 输出                         | 频率 | 模型          |
| ----------------- | ------------- | -------------------------- | -- | ----------- |
| **意图 → Plan（任务级规划）** | 自然语言 + 任务统计 | Plan（JSON，3 种 stage kind，受 schema 约束） | 低  | 大模型         |
| **偏离重规划**          | Plan 执行统计    | 新 Plan（JSON，受 schema 约束）       | 低  | 规则（阈值触发）→ 模型 |
| **整本策略切换**        | 任务统计         | Strategy 枚举                  | 低  | 规则 → 模型      |

**除此之外，所有环节必须是确定性代码。** 包括：格式嗅探、链路路由、解析执行、指标计算、兜底档位判定、门控判定、合并组装、输出。

> 特别注意：**页级决策（格式路由、兜底档位、算子选择、是否续试、何时升级，含失败归因）一律由确定性规则实现，不由模型决定**。模型只参与任务级三处，且每任务调用 ≤ 8 次；否则同一输入两次运行可能给出不同档位或不同处理路径，破坏可复现性。

### 2.3 模型放置策略

| 输出形态      | 用什么              | 判定标准         | 本产品例子                      |
| --------- | ---------------- | ------------ | -------------------------- |
| 完全确定      | 规则 / 传统算法        | 有唯一正确答案      | 格式嗅探、哈希去重、页数统计、字符密度、兜底档位判定 |
| 封闭标签集     | **小模型**（本地推理）    | 分类 / 打分 / 排序 | 业务域分类、表格结构合理性（页级归因已收敛为规则，见 2.2）         |
| 开放文本 / 计划 | 大模型（schema + 沙箱） | 需要开放集推理      | 自然语言 → RulePack、新故障诊断      |
| 需要人承担后果   | 人                | 责任边界         | 损坏文件确认、规则包上线、升级审批          |

**小模型部署要求**：ONNX Runtime / vLLM / Triton，模型文件随包分发，无外网调用，支持 CPU 推理，输出必须是 `label + score`，禁止自由文本。

### 2.4 自治级别

| 级别                   | 行为                | 适用场景        | 人工介入点 |
| -------------------- | ----------------- | ----------- | ----- |
| **L0 建议**            | 只生成方案，不执行         | 陌生数据、首次接入   | 全部    |
| **L1 单步**（Copilot）   | 每步生成计划 → 人确认 → 执行 | 生产库、高风险数据   | 每个动作  |
| **L2 整链**（Autopilot） | 整链自动，受预算与门控约束     | 已标定规则包、重复任务 | 仅升级   |
| **L3 自愈**            | 整链 + 自动修复，预算内     | 成熟场景        | 仅预算耗尽 |

### 2.5 "Agent 驱动"的反例（验收时用于排除伪实现）

以下均**不算** Agent 驱动，验收时直接否决：

- 固定顺序的 if-else 流水线，只是命名为 Agent
- 每一步都调用大模型（成本失控，且不可复现）
- 让大模型直接生成 SQL 并执行到生产库
- 让大模型直接修改解析工具代码
- 没有预算、没有终止条件的循环
- 质检由解析模块自己做（既当运动员又当裁判）
- 用模型判定兜底档位，导致同一输入结果不可复现

### 2.6 角色间契约与交互开销

四角色之间只有三条消息，全部为结构化 schema，禁止自由文本。**这三条消息就是"交互逻辑"，除此之外不存在角色之间的直接调用。**

| 消息               | 从 → 到             | 必填字段                                                                                                   | 落库表                   |
| ---------------- | ----------------- | ------------------------------------------------------------------------------------------------------ | --------------------- |
| `ParseRequest`   | 调度器 → 解析器         | `task_id, doc_id, page_range, engine, params_hash, rulepack_hash, resource_hint, doc_affinity_key`     | `page_artifact` 的来源记录 |
| `PageReport`     | 质检器 → 调度器 / 修复执行器 | `doc_id, page_no, verdict, extract_quality, defects[], attribution, recommended_action, qc_confidence` | `page_report`         |
| `OperatorResult` | 修复执行器 → 质检器       | `doc_id, page_no, candidate_artifact_id(可空), changed, cost, notes`                                     | `action`              |

**三条硬性约束**

1. **解析器不得直接调用质检器或修复执行器**，必须经调度器。否则依赖图不可控、无法审计、预算无法集中扣减。
2. **质检结果必须先落库再触发下游**。不允许"消息到了但库里没有"，否则崩溃重启后无法判断这一页到底判过没判过（见 4.8.5）。
3. **`OperatorResult.changed == false` 必须被视为"此路不通"**，立即停止该动作链，不得重试同参数（见 4.5.9）。

**交互开销预算（上限，超出即为设计错误）**

| 开销项            | 上限                            | 说明                                                 |
| -------------- | ----------------------------- | -------------------------------------------------- |
| 每次任务的角色间消息条数   | ≤ `4 × 批数 + 3 × fail 页数 + 常数` | 若与"总页数"成正比，说明实现退化成了逐页消息                            |
| 页级归因调用           | 规则实现，0 模型调用（V2.3）       | 失败归因已收敛为确定性规则（见 2.2）；任务级偏离重规划若采用模型实现，其调用计入 `max_model_calls` |
| artifact 跨进程传递 | **仅解析器 → 控制面一次**，方向单向         | 质检与修复**不得**把 artifact 传给第三个进程（见 4.3.7 的边界划分）       |
| 单页状态往返队列次数     | ≤ 3（对应 T2/T3 总预算）             | 每次往返 ≥ 调度响应 1s，3 次即 ≥ 3s，这是可接受上限                   |
| 同步等待           | 禁止角色间长同步等待                    | 一律事件驱动 + 状态落库，不允许"发出去等回包"式编排                       |

## 三、用户角色与使用场景

### 3.1 用户角色

| 角色        | 核心诉求                     | 与 Agent 的交互方式  |
| --------- | ------------------------ | -------------- |
| 数据处理操作员   | 批量上传 / 接入，自动处理，查看结果，处理异常 | 对话 + 看板 + 待办队列 |
| 业务配置人员    | 配置规则、个性化要求，无需开发介入        | 对话 + 可视化配置     |
| 系统管理员     | 部署、节点管理、监控、容量规划          | 管理台            |
| 开发人员      | 新增格式插件、扩展能力，不影响现有流程      | 插件 SDK         |
| **业务负责人** | 关心准确率、成本、合规、可追溯          | 报表 + 审计        |

> **交互形态的实现时点**：上表列出的对话界面、看板、待办队列、管理台均为 P2 交付物。P0 / P1 阶段这些角色的能力通过 API / CLI / 结果文件 / 处理报告承载，验收标准（第七章）不含任何界面项。详见 8.3。
>
> **P0 的入口形态**（见 4.8.8）：`dataagent up` 一条命令拉起服务并打印本地地址，浏览器打开即用；同时提供只读状态页 `/status` 与 `dataagent status / logs / plugin / doctor` 子命令。**CLI 是唯一入口，Web 由 CLI 拉起**，二者是同一个进程的两个壳，不是两套产品。

### 3.2 典型使用场景

#### 场景一：批量财报文档处理

- **描述**：收到上百份上市公司年报 PDF，需提取核心财务数据、校验报表完整性、按标准格式导出。
- **Agent 参与点**：格式判定 → PDF 页级路由 → 业务域识别（小模型）→ 页级质检 → 兜底档位判定 → 勾稽失败归因 → 修复动作选择。
- **个性化**：不同行业财报的校验规则、提取字段、输出格式，通过 RulePack 配置。
- **验收看板**：STP 率、复杂页占比、单页成本、勾稽通过率。

#### 场景二：多格式数据归集入库

- **描述**：业务部门产生 CSV、TXT、PDF 等多种格式文件，需统一解析、校验、结构化后写入数据库。
- **Agent 参与点**：边界处理 → 格式判定 → 插件路由 → 字段映射（RulePack）→ 入库前校验。
- **个性化**：不同数据源的校验规则、字段映射、入库标准。

#### 场景三：合规文档批量审核

- **描述**：法规、合同等文档批量入库前，校验格式完整性、必备要素缺失、内容合规性。
- **Agent 参与点**：业务域分类 → 规则包匹配 → 合规项校验 → 异常分级。
- **个性化**：不同类型文档的合规校验项、异常等级。

#### 场景四：数据库 / API 定时拉取

- **描述**：从 ERP / 财务系统定时拉取报表附件，自动处理并回写结果。
- **Agent 参与点**：自然语言描述拉取条件 → 生成 TaskSpec → 预览确认 → 定时执行。
- **约束**：只读账号、表白名单、参数化模板、行数上限、敏感字段脱敏（见 4.1.3）。

### 3.3 场景与能力映射

| 场景    | 接入         | 路由   | 解析     | 质检       | 兜底    | 规则 | 输出         |
| ----- | ---------- | ---- | ------ | -------- | ----- | -- | ---------- |
| 财报处理  | 文件夹/上传     | ✅ 两级 | PDF 插件 | L1+L2+L3 | T0–T3 | ✅  | JSON/Excel |
| 多格式归集 | 文件夹/DB/API | ✅ 两级 | 多插件    | L1+L2    | T0–T2 | ✅  | DB/CSV     |
| 合规审核  | 文件夹/上传     | ✅ 两级 | PDF 插件 | L1+L3    | T0–T2 | ✅  | 审核报告       |
| 数据库拉取 | DB/API     | ✅ 两级 | 多插件    | L1+L2    | T0–T2 | ✅  | 回写         |

## 四、功能需求

### 4.1 数据接入模块（AI 驱动）

#### 4.1.1 功能概述

统一数据入口。Agent 不直接操作数据源，而是**生成 TaskSpec**，由确定性连接器执行。所有接入默认只读。

#### 4.1.2 接入方式

| 方式     | 能力             | 触发           | 约束              |
| ------ | -------------- | ------------ | --------------- |
| 文件夹监听  | 配置目录，新增文件自动触发  | inotify / 轮询 | 路径白名单、只读        |
| 手动上传   | Web 单文件 / 批量上传 | 用户操作         | 大小限制、病毒扫描       |
| API 接入 | 标准 REST 接口推送任务 | 外部系统         | 鉴权、限流           |
| 数据库拉取  | 配置数据源，定时/增量拉取  | 调度器          | 只读账号、表白名单、参数化模板 |

#### 4.1.3 数据库连接器约束（安全红线）

| 约束 | 要求                           |
| -- | ---------------------------- |
| 账号 | 强制只读，禁止 DDL/DML              |
| 表  | 白名单，禁止 `select *` 全库扫描       |
| 查询 | 只允许**参数化模板**，禁止 LLM 生成任意 SQL |
| 行数 | 单次 ≤ 10,000 行，超出分批           |
| 超时 | 单查询 ≤ 30s                    |
| 脱敏 | 身份证、手机号、银行卡等字段自动掩码           |
| 审计 | 每次查询记录：谁、何时、哪个模板、多少行         |

#### 4.1.4 TaskSpec（任务规格）

```yaml
task:
  source:
    type: folder | upload | api | db
    connection: <连接器 ID>
    path: /2024/annual_reports
    filter: "*.pdf"
    since: 2024-01-01
  scope:                      # V2.1 新增：页级筛选
    page_filter: "has_table == true and pdf_type == 'text_based'"
    skip_pages: "is_toc == true"
  target:
    format: json
    schema: financial_report_v2
  quality:
    rulepack: cn_a_share_annual_v1
    stp_target: 0.85
    escalate_on: [table_break, low_extract_quality]
  budget:
    max_cost_per_doc: 0.5
    max_attempts_per_page: 3
    max_wall_time_s: 600
  profile_speed: quality | balanced | fast     # V2.2：性能档位（见 4.4.12）
  fallback:                                    # V2.2：复杂页的外部增强与降级
    enhancer: local_ocr | mineru | none         # 默认 local_ocr
    on_unavailable: mark_only | fail_doc        # 默认 mark_only
  delivery:                                    # V2.2：分级交付
    gap_tolerance: 0.05                        # gap 页占比 > 5% 判 needs_review
  resources:                                   # V2.2：资源规格，auto 由启动自检给出建议值
    profile: auto | 8c16g | 16c64g | 32c128g | custom
    workers: auto
    batch_pages: auto
  plan:                                        # V2.3：任务级执行规划（可选，缺省 = 单策略直跑）
    version: 1
    stages:
      - id: probe                 # 探路：先跑 1-100 页
        kind: processing
        scope: { pages: "1-100" }
        strategy: quality
      - id: decide                # 分支：读探路统计
        kind: decision
        on: { metric: stp_rate, window: probe }
        branches:
          - when: "stp_rate >= 0.85"   # json-logic，白名单仅限统计指标
            goto: bulk_fast
          - when: "stp_rate < 0.75"
            goto: bulk_quality
          - else: true
            goto: bulk_balanced
      - id: bulk_fast
        kind: processing
        scope: { pages: "101-" }
        strategy: fast
    guards:
      max_model_calls: 8          # 任务级模型调用硬上限
      max_replans: 3
      max_wall_time_s: 3600
  autonomy: copilot | autopilot
```


**规则**：

1. TaskSpec 必须通过 JSON Schema 校验；生成后先预览（文件列表 / 前 20 行），人工确认后才执行（L1 及以上）。
2. `scope.page_filter` 与 `skip_pages` 使用与 RulePack 同一套受限表达式引擎（JSONLogic / CEL），白名单字段仅限 PageProfile 的 `class` / `layout` / `signals` 三组。
3. **禁止 `page_filter` 引用 `extract_quality`**：质量分是解析后的产物，若允许它决定哪些页被处理，会形成因果循环（被处理的页才有质量分，未处理的页永远没机会被判定为需要处理）。
4. **`profile_speed` 不得影响 L1 校验**。fast 档只允许削减 L2 抽样比例与增强轮次，L1 必须全量（见 4.4.11、4.4.12）。
5. **`fallback.enhancer` 必须是配置项，不得写死**。未接外部增强器时默认 `local_ocr`；若客户环境连本地 OCR 都不具备，落到 `mark_only`（只标记不处理），并在报告中显式标注。
6. **`resources` 由启动自检给出建议值，用户可覆盖，但覆盖后必须做可行性校验**（见 4.8.6）。填写超出机器能力的值时直接告警并降级，不允许"改完偷偷 OOM"。
7. **`plan` 是任务级执行规划，可选**。不提供 `plan` 时按单一策略直跑（等价于单段 `processing`）。提供时 `stages` 只允许 3 种 `kind`（`processing` / `decision` / `replan`），禁止自由图结构。
8. **分支表达式用受限表达式引擎**（与 `page_filter` / RulePack 同一套，白名单仅限统计指标如 `stp_rate`）；`plan` 一经确认即冻结，执行与重放必须逐字一致，禁止执行期改动。
9. **`guards` 三项硬上限**：`max_model_calls`（默认 8，任务级模型调用总上限）、`max_replans`（默认 3）、`max_wall_time_s`（默认 3600）。任一超出即停止该 Plan，交付带缺口的最终结果，不允许无限重规划。

#### 4.1.5 接入预处理

| 能力    | 做法                                                                            |
| ----- | ----------------------------------------------------------------------------- |
| 完整性检测 | magic bytes + 头部结构解析 + 页树可读性                                                  |
| 类型识别  | 内容特征嗅探，**不依赖后缀名**。判定逻辑与阈值见 **4.2.5**（一级格式判定器），本节不重复实现                         |
| 去重    | 内容哈希（SHA-256），重复文件直接复用已有结果                                                    |
| 自动分类  | 按家族归类（pdf / tabular / text / image）；未分类文件进入 `unclassified` 桶。与上一条同为 4.2.5 的输出 |

> 说明：接入预处理只负责"接收、去重、登记"，**不做格式判定**。格式判定统一由 4.2.5 的判定器完成，二者共用同一次扫描结果（4.2.5 规则 3）。

#### 4.1.6 异常拦截

- 损坏 / 截断 / 加密 / 空文件 / 不支持格式：拦截，**不进路由**，不进主链路
- 进入"待确认队列"，带诊断信息（哪一步失败、错误码、建议）
- 全量记录接入日志，支持按文件追溯
- **拦截必须发生在任何解析插件被调用之前**：否则插件抛出的异常会顶替掉诊断信息，人工看不到"哪一步失败"

#### 4.1.7 输入输出

- **输入**：原始文件、连接器配置、TaskSpec
- **输出**：标准化 Task 记录（含文件哈希、来源、优先级、状态）

#### 4.1.8 文件级体检（防崩溃的第一道闸）

4.1.5 的"完整性检测"只回答"这个文件能不能读"。本节回答另一个问题：**"处理这个文件会不会把进程搞死"**。两件事必须分开，因为前者的失败是"这个文件处理不了"，后者的失败是"整个任务中断"。

**检查项与阈值（全部 O(1) 或 O(对象数)，单文件开销 < 5ms）**

| #  | 检查           | 方法                  | 阈值                          | 不通过后果              |
| -- | ------------ | ------------------- | --------------------------- | ------------------ |
| 1  | 空文件 / 超大文件   | 文件大小                | `0 < size ≤ 2GB`（可配）        | 拒收                 |
| 2  | magic bytes  | 头 8 字节              | 与后缀声明的格式一致                  | 拒收或改判家族            |
| 3  | 头部 + trailer | 是否存在 `%%EOF`、是否被截断  | 缺失即截断                       | 标记 `repairable`    |
| 4  | xref 可解析性    | 交叉引用表 / xref stream | 可重建或可顺序扫描                   | `repairable`，重建后重入 |
| 5  | 页树可遍历        | `/Pages` 遍历，比对声明页数  | 声明页数 = 实际可读页数               | `repairable` / 拒收  |
| 6  | **页树深度**     | 递归深度计数              | **≤ 50 层**                  | **拒收**（栈溢出风险）      |
| 7  | **单页尺寸**     | `/MediaBox` 宽高      | **≤ 14400 pt（200 英寸）** 任一方向 | 标记可疑，渲染前按比例降采样     |
| 8  | 对象总数         | xref 条目数            | `≤ 200 万`                   | 标记可疑               |
| 9  | 资源字典嵌套深度     | 递归深度                | `≤ 30` 层                    | 标记可疑（递归溢出）         |
| 10 | 流解压比         | 抽样 10 个流，解压后/压缩前    | `≤ 200:1`                   | 拒收（zip 炸弹）         |
| 11 | 加密           | `/Encrypt`          | 有密码且未提供                     | 拒收，入待确认队列          |

**三态输出**

| 状态           | 含义                         | 去向                        |
| ------------ | -------------------------- | ------------------------- |
| `ok`         | 全部通过                       | 进一级格式判定（4.2.2）            |
| `repairable` | 结构问题可修（xref 损坏、尾缺失、页树轻微异常） | 先重建再进路由；修复失败则转 `rejected` |
| `rejected`   | 不可处理或不安全                   | **不进路由**，入待确认队列，带诊断码      |

**三条必须遵守的规则**

1. **体检必须在任何解析插件被调用之前完成**（与 4.1.6 一致，此处加强）。第 6/7/9/10 项专门针对"恶意或损坏文件导致进程崩溃"，这类崩溃是段错误，Python 层捕获不到。
2. **页树深度超限必须硬拒，不得"尽力而为"**。超深嵌套的 `/Pages` 树会让递归解析爆栈，而爆栈发生在 Rust 扩展内部时，整个 Python 进程直接退出，连日志都来不及写。
3. **第 7–9 项标记为"可疑"而非"拒收"**：真实业务里存在大图纸（工程图、A0 幅面），直接拒收会误伤。正确做法是降采样后继续，同时把这一页标记为高风险页，允许它在渲染阶段被资源守卫熔断（4.8.6）。

### 4.1.9 任务级规划（Plan）与编排边界（V2.3 新增）

**一句话定位**：Agent 的灵活性只存在于"计划生成时刻"，不存在于"执行时刻"。

**核心语义**

1. **模型只负责生成计划，不负责执行时判断**。`Plan` 由模型（或规则模板）生成 → 冻结落库 → 执行严格按 Plan 走；执行路径确定、产物可复现。
2. **3 种 stage kind 即全部**：`processing`（处理一段页范围）、`decision`（对统计指标求值、按分支跳转）、`replan`（请求重规划）。禁止自由图结构——否则确定性编排退化成解释器。
3. **分支条件复用 `rules/` 的受限表达式**（json-logic），白名单仅限统计指标，无代码执行、可静态分析。
4. **重放与一致性**：重放历史任务用同一 `plan_version`，结果逐字一致；重规划产生新 `plan_version`，落库、可 diff、计入 `max_replans`，超出即停止并告警。
5. **页级决策边界**：`plan` 只决定"处理策略"（探路范围、整本档位、分支跳转），**不代替页级决策**（路由 / 档位 / 算子 / 续试 / 升级）。页级决策一律确定性规则（见 2.2）。

**与既有 TaskSpec 的关系**：`TaskSpec` 是参数（`stp_target`、`budget`、`profile_speed`、`fallback`），`plan` 是执行策略（探路 → 分支 → 批量）。缺省 `plan` 时按单一策略直跑，行为与 V2.2 一致。

**验收锚点**：同一 `plan_version` 重放结果逐字一致；任务级模型调用 ≤ 8 次；重规划超过 `max_replans` 后停止并交付带缺口结果（对应 spec FR-026 / SC-014）。

### 4.2 格式判定与链路路由模块

#### 4.2.1 功能概述

按内容而非后缀选择处理链路。路由分两级：**一级做边界与格式判定（纯规则），二级只在 PDF 家族内做页级路由**。路由必须是声明式注册表 + 规则决策，不是散落的 if-else。

#### 4.2.2 两级路由

**一级：边界处理与格式判定（确定性，不调用任何解析插件）**

```
完整性检测 → magic bytes → 容器结构解析 → 家族归属
  ├─ 损坏 / 截断 / 加密 / 空文件 → 拦截，进待确认队列，带诊断码（4.1.6）
  └─ 家族：pdf | tabular | text | image | unknown → 进入二级或直接派插件
```

**为什么一级必须独立于任何解析插件**

1. **损坏文件必须在解析之前拦截。** 否则插件抛异常会顶替诊断信息。
2. **非 PDF 格式不能用 PDF 分类器判。** PDF 分类能力只认 PDF，对 CSV 调用会得到"不是 PDF"的无用结论，还白付 10–50ms 启动开销。
3. **一级必须是纯规则且可复现。** 后缀名不可信，但 magic bytes + 结构特征可复现，且这一层结果要写进审计。

**二级：仅 `pdf` 家族内，调用 PDF 插件的 `pdf.classify` 能力做页级路由**

| 输入                 | 输出                                                                                                                                          | 用途                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `detect_pdf(path)` | `pdf_type`、`page_count`、`pages_needing_ocr`、`pages_with_tables`、`pages_with_columns`、`is_complex_layout`、`confidence`、`ocr_reasons_by_page` | **逐页分配链路** + 页面画像的 `class` / `layout` 分组 |

`detect_pdf` **不做抽取、不产 Markdown**（`markdown = None`，`cmap_gaps` 恒为空）。它只承担路由与画像，不承担解析——这正是两级路由能省成本的原因。

**逐页分配规则**

```
detect_pdf 结果
  ├─ pdf_type == scanned（整本无文本层）→ 整本一次派给 OCR 插件，不逐页派
  ├─ pdf_type == image_based           → **先用 PDFium 逐页 render 成图**，再派 engine.image / engine.vlm
  │                                      （engine.image 接的是 PNG/JPEG 魔数，不能直接吃 PDF；这一步引入 PDFium 依赖）
  ├─ 页在 pages_needing_ocr 中          → OCR 插件（GPU 子链）
  ├─ 页不在 pages_needing_ocr 中         → PDF 插件（page 级入队，批级执行）
  └─ is_complex_layout == true         → 标记复杂页，L1 硬门控按复杂页档位执行
```

**链路注册表**

| 级  | 链路 ID             | 判定依据                    | 插件                               | 成本             |
| -- | ----------------- | ----------------------- | -------------------------------- | -------------- |
| 一级 | `reject`          | 完整性检测失败                 | 无（拦截）                            | 0              |
| 一级 | `pdf.*`           | `%PDF` magic + 页树可读     | 见二级                              | —              |
| 一级 | `tabular`         | 分隔符一致性 > 0.8            | `engine.csv`                     | 极低             |
| 一级 | `text`            | 可检测字符集                  | `engine.text`                    | 极低             |
| 一级 | `image`（非 PDF 内嵌） | PNG/JPEG/TIFF magic     | `engine.image`                   | 高              |
| 二级 | `pdf.native`      | 页不在 `pages_needing_ocr` | `engine.pdf`（`pdf.text.extract`） | 极低（~10–25ms/页） |
| 二级 | `pdf.ocr`         | 页在 `pages_needing_ocr`  | `engine.ocr`                     | 高（2–5s/页）      |
| 二级 | `pdf.vlm`         | OCR 后仍 fail，或复杂页升级      | `engine.vlm`                     | 极高             |

#### 4.2.3 路由决策

**输入**：一级判定结果、二级分类结果、插件能力、成本预算。  
**输出**：`{chain_id, page_range, engine, params, reason, profile_snapshot}`。

- `reason` 必须落库，用于可解释性与事后分析
- `profile_snapshot` 是决策当时的页面画像快照——**画像本身是路由依据，不存下来事后无法解释"为什么这页走了 OCR"**
- **低置信处理**：`class_confidence` 低时不硬选。先抽 3 页做小样本试跑，比较质量/成本后再决定整链路

#### 4.2.4 功能点

1. 一级判定：magic bytes + 结构解析 + 采样，纯规则
2. 二级判定：调用 PDF 插件 `pdf.classify`，输出页级路由建议
3. 链路注册表的增删改查（管理台）
4. 路由策略配置（成本优先 / 质量优先 / 均衡）
5. 路由结果可解释（decision trace + profile_snapshot 落库）
6. 未知格式进入 `unclassified` 并告警，不静默丢弃

#### 4.2.5 一级格式判定器（自建模块，不由插件提供）

**本节用于消除一个关键误读：`pdf.classify` 只做"PDF 内部类型"判定，不做"文件格式"判定。** 文件级分类器必须自建——它甚至不该向 PDF 插件提"这是不是 PDF"这个问题（对 CSV 调用只会得到"不是 PDF"，还白付 10–50ms）。

**职责边界**

| 判定                                                          | 谁做                  | 说明                     |
| ----------------------------------------------------------- | ------------------- | ---------------------- |
| 文件家族：`pdf` / `tabular` / `text` / `image` / `unknown`       | **自建（本节）**          | 纯规则，不调用任何解析插件          |
| PDF 内部类型：`text_based` / `scanned` / `image_based` / `mixed` | 插件 `pdf.classify`   | **仅对已判定为 pdf 家族的文件调用** |
| 页级链路分配                                                      | 自建决策器，消费插件输出（4.2.3） | 决策逻辑在系统内，不在插件内         |

**判定流水线（顺序不可调换）**

| 序 | 层      | 判什么                                     | 依据                                                                      | 后果                       | 成本   |
| - | ------ | --------------------------------------- | ----------------------------------------------------------------------- | ------------------------ | ---- |
| 1 | 体积与空文件 | 0 字节、超上限                                | 文件元数据                                                                   | 拒收                       | O(1) |
| 2 | 魔数     | 头 8 字节                                  | `%PDF-` / `PK\x03\x04` / `\x89PNG` / `\xFF\xD8\xFF` / `II*\0` / `MM\0*` | 强判据，定位候选家族               | O(1) |
| 3 | 容器结构   | PDF 页树 / xlsx 内 `workbook.xml` / 图片头内宽高 | 结构解析（不抽正文）                                                              | 区分"真 PDF"与"改后缀的文本"；防解码炸弹 | ms 级 |
| 4 | 编码检测   | 合法 UTF-8 / GB18030 / UTF-16 占比          | 前 64 KB 字节分布                                                            | `text` 家族 vs `unknown`   | ms 级 |
| 5 | 分隔符采样  | 前 100 行分隔符一致性                           | 抽样统计                                                                    | `tabular` 家族             | ms 级 |
| 6 | 家族归属   | 合成上述结果                                  | 规则表                                                                     | 写入 `Document.family`     | O(1) |

**采样预算（硬约束）**：一级判定单文件开销 **≤ 50ms**，且**最多读取前 256 KB**。理由：1000 份文件的一级判定必须秒级完成，不能为了一份 2 GB 的 CSV 扫全文。超过 256 KB 部分不参与格式判定。

**判定结果三态（不允许只有"成功/失败"两种）**

| 状态             | 条件                         | 动作                                                          |
| -------------- | -------------------------- | ----------------------------------------------------------- |
| `confident`    | 强判据命中且结构自洽                 | 直接派插件                                                       |
| `ambiguous`    | 弱判据冲突（如：文本编码，但分隔符一致性仅 0.6） | **不猜**。取前 50 行做小样本双跑（两个候选插件各跑一次），按 4.2.3 的"低置信处理"比较质量与成本后决策 |
| `unclassified` | 无任何判据命中                    | 归 `unknown`，进待确认队列并告警，**不得静默丢弃**（4.2.4 第 6 条）               |

**家族判定阈值（初值，需在真实语料上标定）**

| 家族        | 强判据                         | 弱判据（补充确认）                         |
| --------- | --------------------------- | --------------------------------- |
| `pdf`     | `%PDF-` 魔数                  | 页树可读、xref 可解析                     |
| `tabular` | 无魔数，但为合法文本编码                | 前 100 行中单一分隔符使列数方差 ≤ 1 且一致性 > 0.8 |
| `text`    | 无魔数，合法编码字符占比 > 0.95         | 行长度方差大、无稳定分隔符                     |
| `image`   | PNG / JPEG / TIFF / WebP 魔数 | 头内宽高合法且 ≤ 尺寸上限（4.1.8）             |
| `unknown` | 以上皆不命中                      | —                                 |

**四条必须写死的规则**

1. **后缀名只作提示，不作判据。** 后缀与魔数冲突时以魔数为准，并记一条 `extension_mismatch` 事件（可运营信号：反映客户上游数据治理状况）。
2. **魔数不是充分条件。** `%PDF-` 也可能是一个被塞进别处的内容；必须过第 3 层结构确认才归 `pdf`。反之，魔数正确但页树不可读的文件应归 `repairable`（4.1.8），**不是** `unknown`——两者的处理路径完全不同。
3. **家族判定与文件体检合并为一次扫描**，输出 `Document.family` + `Document.health`。分两次扫等于同一个文件付两遍 IO，1000 份场景下这是秒级与分钟级的差别。
4. **一级判定结果必须落库并进审计**，因为它决定了后续所有路由，不可复现就无法解释"为什么这份文件走了 CSV 链路"。

**扩展方式**：新增家族（docx / xlsx / html 等）= 在配置文件加一条判定规则 + 注册一个 `engine` 插件，**不改决策器代码**（与 5.5 一致）。这条在 P0 就要成立，因为 P1 必然要加格式。

**工作量**：约 1 人周（规则实现 + 阈值标定 + 单测语料）。属于"简单但必须"的工作，不是难点；但**它不做，所有格式路由都无法工作**。

### 4.3 插件化解析处理模块

#### 4.3.1 功能概述

通过统一契约插件提供解析能力。**插件契约见 5.1**，本节只定义能力要求。

**所有格式的解析都以插件形式提供**：PDF、CSV、TXT、图片各自是独立插件，注册进同一张表，由路由按页/按文件派活。新增一种格式 = 新增一个插件，核心代码零改动。

#### 4.3.2 插件体系要求

| 要求        | 说明                                                                                           |
| --------- | -------------------------------------------------------------------------------------------- |
| 统一契约      | 所有插件实现同一 manifest + 同一输入输出 schema                                                            |
| **能力多接口** | 一个插件可声明多个 `capability`，被不同消费者调用。**路由决策器只消费 `*.classify` 类能力，解析调度器只消费 `*.extract` 类能力**，两者不交叉 |
| 热插拔       | 新增格式无需修改核心，动态加载                                                                              |
| 多插件并存     | 同一格式可注册多个引擎，按优先级/成本/质量选择                                                                     |
| 版本化       | 插件版本参与幂等键，升级不影响历史结果                                                                          |
| 资源声明      | 插件必须声明 CPU/GPU/内存/超时需求，调度器据此分配                                                               |
| 确定性声明     | 必须声明 `deterministic / stochastic / model`，影响可重放策略                                            |
| 可选依赖声明    | 插件必须声明运行时可选依赖（如 OCR 所需的外部二进制与模型），离线部署据此校验                                                    |

> **为什么需要"能力多接口"**：PDF 是唯一同时需要"分类"和"解析"两种能力的格式（先分类才能按页派活，再解析才出内容）。若不允许多 capability，就只能拆成两个插件（分类插件 + 解析插件）或把分类写死在路由模块里，前者冗余、后者破坏插件化。允许一个插件声明两个能力，是这里的正确解法。
>
> 新增 TXT 解析器只需实现 `*.extract`；新增别的格式分类器只需实现 `*.classify`。契约本身不变。

#### 4.3.3 PDF 解析插件（`engine.pdf`）

**定位**：注册在插件体系里的一个 `engine` 插件，声明 `pdf.classify` 与 `pdf.text.extract` 两个能力。它**不是唯一引擎**，是 PDF 家族当前唯一的 `extract` 实现。CSV / TXT / 图片各有自己的插件，路由按格式与页型派活。

**能力声明**

```yaml
id: engine.pdf
kind: engine
provides:
  - capability: pdf.classify       # 供路由：pdf_type + 页级路由建议 + 版式画像（不产内容）
  - capability: pdf.text.extract   # 供解析：页级 Markdown + text_items + 表格
determinism: deterministic         # 纯函数：同输入同输出 → 允许缓存、禁止无变化重跑
concurrency: reentrant
sandbox: none                      # builtin，同进程调用
```

**调用模型：每文档 1 次分类 + N 次批量抽取**

| 阶段       | 接口                                               | 产出                                                                                                                             | 调用次数                  |
| -------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | --------------------- |
| 路由（二级）   | `detect_pdf(path)`                               | `pdf_type`、`pages_needing_ocr`、`pages_with_tables`、`pages_with_columns`、`is_complex_layout`、`confidence`、`ocr_reasons_by_page` | **1 次 / 文档**          |
| 解析（批级）   | `extract_pages_markdown(path, pages=[...])`      | 逐页 `markdown` + `needs_ocr` + `ocr_reason`                                                                                     | **⌈页数 / 批大小⌉ 次 / 文档** |
| 解析（需坐标）  | `extract_text_with_positions(path, pages=[...])` | `text`/`bbox`/`font`/`font_size`/`rotation`/`fill_color`/`baseline_shift`/`mcid`                                               | 同上                    |
| 标题层级     | `extract_structure_elements(path)`               | `(page, mcid, role)` → `H1..H6`/`P`/`Table`                                                                                    | 1 次（仅 tagged PDF）     |
| 局部重抽（T2） | `extract_text_in_regions(path, page_regions)`    | 区域文本 + 逐区域 `needs_ocr`                                                                                                         | 按需                    |

**两次调用不是重复劳动，是职责分工**

| 调用                       | 做什么                      | 不做什么                     |
| ------------------------ | ------------------------ | ------------------------ |
| `detect_pdf`             | 判类型、判哪几页需要 OCR、判版式复杂度    | 不抽正文、不产 Markdown、不算字符覆盖率 |
| `extract_pages_markdown` | 抽正文、产页级 Markdown、产编码缺口诊断 | 不做格式判定、不决定路由             |

预分类开销占比：`0.5–2.5ms/页 ÷ 23ms/页 ≈ 2%–11%`。这是为"能选对解析插件"付的必要成本，不是浪费。

**页码基准统一（防"差一页"，必须写进封装层）**

该插件的不同接口、甚至**同一个返回对象内部**，页码基准并不一致：

| 接口 / 字段                                                                                | 基准            |
| -------------------------------------------------------------------------------------- | ------------- |
| `classify_pdf` → `pages_needing_ocr`                                                   | **0-indexed** |
| `extract_pages_markdown(pages=[...])` **入参**                                           | **0-indexed** |
| `PagesExtractionResult.pages[].page`                                                   | **0-indexed** |
| `PagesExtractionResult.pages_with_tables` / `pages_with_columns` / `pages_needing_ocr` | **1-indexed** |
| `process_pdf_with_ocr(page_numbers=[...])` 入参                                          | 1-indexed     |
| `detect_pdf` / `process_pdf` → 全部页号字段                                                  | 1-indexed     |
| `TextItem.page` / `StructureElement.page`                                              | 1-indexed     |

注意第三行与第四行：**`extract_pages_markdown` 一次调用同时返回两种基准的页号**（`pages[].page` 是 0-indexed，而 `pages_with_tables` 是 1-indexed）。按"接口级"统一转换一定会错，必须**按字段级**转换。

硬性要求：

1. **系统内部一律 1-indexed**（与 PDF 自然页码一致），只在插件封装层做转换，转换点全工程只允许存在一处。
2. 封装层必须提供断言而不是注释：`extract_pages_markdown(path, pages=[k])` 后，`pages[0].page == k`，且若该页有表，则 `k+1 in pages_with_tables`。
3. 该断言作为单元测试固定下来。理由：200 页文档里"差一页"的表现是"第 82 页的问题记为第 83 页"，人工核对几乎发现不了，但会把整条缺陷定位链、修复回填、报告页码全部带偏。

**批量化是硬要求**

该插件的工作模型是"打开文件 → 抽出指定页"。**逐页调用意味着逐页重新打开并解析同一份文件**：100 页文档会放大 100 倍的打开与页树解析开销，而真正的抽取只占其中很小一部分。

| 要求             | 值                                                  |
| -------------- | -------------------------------------------------- |
| 同一文档的 native 页 | **必须批量抽取**，`pages` 一次传入                            |
| 默认批大小          | 20–50 页/批（可按页大小与内存调整）                              |
| 并行粒度           | **批级并行**，不是页级                                      |
| 跨批顺序           | `extract_pages_markdown` 保持调用方顺序，合并时按 `page_no` 重排 |

**性能口径（统一用此表）**

| 场景                | 官方口径        | 折算（20 页/份）     |
| ----------------- | ----------- | -------------- |
| 分类判定 `detect_pdf` | 10–50ms / 份 | 0.5–2.5ms / 页  |
| 文本型整本抽取           | <200ms / 份  | 10–25ms / 页 上限 |
| 基准语料 200 份端到端     | 0.470s / 份  | 23ms / 页       |

> 依据：pdf-inspector 官方 README 与 opendataloader-bench 结果（Overall 0.875、阅读顺序 0.915、表格 TEDS 0.814、标题 0.788、速度 0.470s/份）。这些数字同时是 4.4.6 与 6.2 质量目标的**基线参照**。

**能力边界（用于防止验收误判）**

| 能力                             | 插件                   | 归属              |
| ------------------------------ | -------------------- | --------------- |
| 文本型 / 扫描件 / 图片型 / 混合 分类        | ✅ `pdf.classify`     | 插件              |
| 逐页 OCR 路由建议 + 机器可读原因           | ✅ `pdf.classify`     | 插件              |
| 版式画像信号（分栏、表格页、复杂度、旋转）          | ✅ `pdf.classify`     | 插件              |
| 位置、字体、字号、旋转、颜色、下划线、上下标、read 顺序 | ✅ `pdf.text.extract` | 插件              |
| 多栏阅读顺序、RTL                     | ✅ `pdf.text.extract` | 插件              |
| Markdown（标题/列表/代码/粗斜体/链接）      | ✅ `pdf.text.extract` | 插件              |
| 编码缺口诊断（`cmap_gaps`）            | ✅（**仅抽取后可用**）        | 插件              |
| 表格识别为 **Markdown 表格**          | ✅                    | 插件              |
| 表格 **cell 级 bbox / 合并单元格结构**   | ❌                    | **自建后处理（T1）**   |
| 跨页表续接                          | ❌                    | 自建（4.7.1）       |
| 页眉页脚剔除                         | ❌                    | 自建（T1）          |
| 页码连续性判断                        | ❌                    | 自建（L3）          |
| 扫描件 OCR 执行                     | ❌（只路由，不内嵌模型）         | `engine.ocr` 插件 |
| 扫描件逐页 OCR 置信度                  | ❌                    | `engine.ocr` 插件 |

**外部依赖（影响 4.8.4 离线交付与安装包体积）**

- 纯文本路径：零外部依赖，不加载任何模型——**成本优势的来源，验收需单独证明**
- OCR 路径：需 PDFium + ONNX Runtime 共享库（`PDFIUM_LIB_PATH` / `ORT_DYLIB_PATH`）；模型首次路由时下载并校验，**离线部署必须预置 `model_directory` + `offline=True`**
- **官方仅发布 Python（PyO3）绑定**，无 Node / WASM 正式发布。Node 侧需自建 FFI 或包 Python 服务——这会影响部署形态选择

#### 4.3.4 并行与分布式

| 层级     | 粒度                        | 调度               |
| ------ | ------------------------- | ---------------- |
| 文件级    | 一个文件一个任务                  | 队列分发             |
| **批级** | 一批（20–50 页）一个子任务，**批内不拆** | 并行 fan-out       |
| 分布式    | worker 无状态                | 按资源标签（cpu/gpu）路由 |

**要求**：

- **同一文档的所有批必须落在同一台机器**（否则每台都要重新打开文件、重新加载字体缓存）
- **OCR 页单独成批**，不与 native 页混批（成本结构不同，且需 GPU 亲和）
- 跨页聚合回控制面

**为什么不是页级并行**：解析成本主要不在"抽这一页"，而在"打开文件、解析页树、建字体缓存"。页级 fan-out 会把这份固定成本按页数倍数放大。批级并行保留并行度，同时把固定成本摊到 20–50 页上。

> **本节定义"跨机怎么分"，单机内部"文件之间怎么并行、worker 开几个"见 4.3.8。** 两者是同一套规则在不同规模下的表现：单机 worker 池与集群节点池使用同一个队列、同一套 `doc_affinity_key`。

#### 4.3.5 页面画像（PageProfile）与分级兜底

**页面画像是"分类结果"与"兜底决策"之间的合同。** 没有它，兜底只能靠"跑失败了换引擎"。

```yaml
page_profile:
  doc_id: <sha256>
  page_no: 1
  class:                          # 来自 pdf.classify（detect_pdf 阶段写入）
    pdf_type: text_based | scanned | image_based | mixed
    class_confidence: 0.0-1.0     # 文档级：分类判断有多确定
    route: native | ocr | vlm     # 逐页路由建议
    route_reason: [string]        # 机器可读，落库
  layout:                         # 来自 pdf.classify（detect_pdf 阶段写入）
    columns: int
    has_table: bool
    is_complex: bool
    rotation: 0 | 90 | 270
  signals:                        # 自建，抽取后写入
    char_density: float
    glyph_coverage: float         # (cmap_gaps.codes - cmap_gaps.unmapped) / cmap_gaps.codes
    empty_region_ratio: float
    header_footer_ratio: float
  quality:                        # 自建，抽取后写入
    extract_quality: 0.0-1.0      # 页级抽取质量分，不依赖真值
    tier: T0 | T1 | T2 | T3       # 兜底档位
```

**时序要求**：`class` 与 `layout` 在路由阶段就有（`detect_pdf` 产）；`signals` 与 `quality` 必须等抽取完成才有（`cmap_gaps` 在 `detect_pdf` 阶段恒为空）。因此 **PageProfile 分两次写入**：路由时写前两段，解析后补后两段。

**`route_reason` 必须原样保留，不得丢弃（复用上游已有能力）**

`route_reason` 的取值来自插件返回的 `ocr_reasons_by_page[].reasons`——这是**上游已经做好的逐页失败原因**，属于白拿的能力。系统对它的要求只有四条：

| # | 要求                                                        | 原因                                                                                          |
| - | --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1 | **原样落库，不裁剪、不映射、不丢弃**                                      | 它是证据。后续归因、报告、人工诊断都以它为准，转换一次就永远回不去                                                           |
| 2 | **到 4.5.7 才映射成缺陷码**，且映射关系放在配置文件，不在代码里写字符串字面量              | 插件的 reason 集合是开放字符串集，版本升级可能新增；写死字面量会在升级后静默失效                                                |
| 3 | **未知 reason 必须透传**，归入兜底缺陷码 `plugin_reason_unknown`，记日志并计数 | 否则插件升级后系统会"静默丢原因"：页面照常进人工队列，但报告写"原因未知"                                                      |
| 4 | **枚举表来自样本实测，不来自文档**                                       | 该字段文档只声明为"machine-readable reason identifiers"，**未给枚举**。技术方案须附一张由 50–100 份真实样本跑出的 reason 清单 |

> 三条能力的来源要分清：`ocr_reasons_by_page`（逐页原因，可复用）、`confidence`（**文档级**分类把握，不可当页级质量分）、`cmap_gaps`（**仅抽取后可用**，编码缺陷的证据）。混用这三者是最容易出错的地方，已在 4.3.3 与 4.4.8 分别约束。

**分级兜底（四档）**

| 档            | 触发条件                                              | 动作                                                          | 预算           |
| ------------ | ------------------------------------------------- | ----------------------------------------------------------- | ------------ |
| **T0 原样采用**  | 无 warning，`extract_quality ≥ τ0`，`route = native` | 直接进 L1                                                      | 0            |
| **T1 后处理修正** | 文本层完好，但表格 / 分栏 / 页眉页脚 / 层级有问题                     | 在插件产物上加工：表格 cell 重建、页眉页脚剔除、跨页续接、标题层级修正                      | 0（纯 CPU，毫秒级） |
| **T2 参数重跑**  | 归因 = 参数不当（分栏阈值、表格模式、粗体判定、页范围）                     | 换参数重跑插件，或 `extract_text_in_regions` 局部重抽；`params_hash` 进幂等键 | 1 次          |
| **T3 换引擎**   | 归因 = 插件能力边界外（无文本层、编码全损、扫描件、极端版面）                  | 换 `engine.ocr` / `engine.vlm` / 对照引擎                        | 最高           |

**与 4.5.3 动作空间的映射**

| 档  | 动作                                                                |
| -- | ----------------------------------------------------------------- |
| T0 | 无                                                                 |
| T1 | `D resegment` + `H strip_header_footer` + `I rebuild_table_cells` |
| T2 | `B tune_params`                                                   |
| T3 | `A switch_engine`、`E ocr_fallback`、`F escalate`                   |

**三条产品要求**

1. **T1 是主力兜底，必须做厚。** 插件的短板是"输出 Markdown 但不管业务结构"（跨页、页眉页脚、cell bbox），这些恰好是纯 CPU 后处理能补的。T1 覆盖率高，STP 才上得去；靠 T3 提 STP，成本优势归零。
2. **预算按档扣减**：T0/T1 不消耗修复预算，T2 计 1 次，T3 计 2 次。不按"尝试次数"扣。
3. **档位判定必须确定可复现**：同一 artifact + 同一画像 → 同一档位。档位判定不准用模型（页级决策一律确定性规则，见 2.2）。

#### 4.3.6 解析输出（PageArtifact）

```yaml
page_artifact:
  doc_id: <sha256>
  page_no: 1
  engine: engine.pdf@1.0.0
  params_hash: <sha256>
  content:
    markdown: string
    text_items: [{text, bbox, font, size, rotation}]
    tables: [{bbox, rows, cols, cells}]      # cells 由 T1 后处理补齐；插件原生仅 Markdown 表
    reading_order: [item_id]
  scores:                                     # V2.1：拆开的三类分数
    class_confidence: 0.0-1.0                 # 文档级，来自 pdf.classify
    extract_quality: 0.0-1.0                  # 页级，自建
  warnings: [string]
  provenance:
    input_hash: <sha256>
    created_at: ts
    duration_ms: int
    tier: T0 | T1 | T2 | T3
```

**要求**：

- artifact 不可变、内容寻址；同一幂等键必须返回同一 artifact
- `tables[].cells` 在插件原生产物中为空，由 T1 后处理填充；未走 T1 的页面该字段为空数组并置 warning，**不得伪造 cell 坐标**
- `class_confidence` 从文档级继承，同文档所有页取值相同；`extract_quality` 逐页独立

#### 4.3.7 页产物规格与内存预算

**这三个数字是批大小、worker 进程数、临时盘预留三个参数的唯一计算依据，必须写死并验收。**

| 内容                          | 单页体量       | 200 页全本    | 说明                                                                     |
| --------------------------- | ---------- | ---------- | ---------------------------------------------------------------------- |
| `content.markdown`          | 3–8 KB     | ~1.5 MB    | 给人读、给下游 LLM 用                                                          |
| `content.text_items`（序列化落盘） | 200–400 KB | 30–60 MB   | 每页 1500–2500 项；每项含 text + bbox + font + size + bold + color + rotation |
| `text_items`（常驻内存对象）        | 0.6–1.2 MB | 120–250 MB | Python 对象有固定开销，约为序列化形式的 3 倍                                            |

**为什么坐标结构比 Markdown 大 50 倍**：Markdown 是排版后的结果，坐标结构是排版之前的事实。**一旦转成 Markdown，坐标永久丢失**，而表格 cell 重建、阅读顺序重排、页眉页脚剔除、按锚点抽字段、跨页表拼接全部依赖坐标。二者必须都保留，不能只留 Markdown。

**内存策略**

| 要求         | 值                                                       |
| ---------- | ------------------------------------------------------- |
| 单批页数       | 20–50 页，**默认 32 页**（16C64G 及以上）；小规格节点按 4.8.6 降档，最低 10 页 |
| 单进程峰值内存预算  | **≤ 50 MB**（32 页 × 1.2 MB + Markdown + 中间结构，含 30% 余量）   |
| 全本产物是否常驻内存 | **禁止**。批完成即落盘释放，全本只在合并阶段流式读取                            |
| 全本合并内存上限   | ≤ 200 MB（流式拼接，不一次性加载 200 页坐标结构）                         |

**跨进程边界（决定质检器与修复算子能不能外置）**

| 内容                                    | 体量           | 是否可以跨进程                      |
| ------------------------------------- | ------------ | ---------------------------- |
| 完整 artifact（markdown + 全部 text_items） | 200–400 KB/页 | **仅在"解析器 → 控制面"通路上传一次**，方向单向 |
| 特征向量（L1 指标 + 缺陷清单）                    | **约 2 KB**   | **可以**。判定逻辑外置时只传这个           |
| 修复算子输入                                | 完整 artifact  | **不可以**。修复要读写坐标结构，必须与解析同进程   |

**结论（设计约束，实现时不得更改）**

1. **质检判定可以独立部署**，因为它只消费特征向量；但**特征提取必须发生在解析进程内**（否则要先传完整 artifact，得不偿失）。
2. **修复算子必须与解析同进程**（4.5.8），它操作完整坐标结构。
3. 任何"把完整 artifact 传给第三方进程做校验"的设计，**直接否决**。

#### 4.3.8 并发模型与 worker 规模

| 维度     | 规则                                              |
| ------ | ----------------------------------------------- |
| 文件之间   | **并行**。有界队列 + 固定 worker 池，一个 worker 同一时刻只处理一个文件 |
| 文件之内   | **按批串行**。同一文件的多批不并行（共享页树与字体缓存，同进程复用收益更高）        |
| 并行粒度   | **批级**（4.3.4）；严禁页级 fan-out                      |
| 同一文档的批 | 必须落在同一节点（`doc_affinity_key`，4.8.2）              |
| OCR 页  | 单独成批，不与 native 页混批                              |

**worker 数与并发的确定方式**

```
worker_进程数 = min( 核数 × 1.25, 可用内存 / 单进程内存上限, 32 )
并发批数      = worker_进程数 × 1     （同进程内不并行跑多个批）
队列上限      = worker_进程数 × 4     （超出即背压，停止拉取新任务）
```

- 系数取 1.25 而非 2：解析是 CPU 密集、IO 等待期短，过度超卖只会加剧上下文切换。
- **1000 份文件不等于 1000 个线程**：文件数是队列长度，不是并发度。
- `worker` 数可由 `resources.workers` 覆盖（4.1.4），但覆盖值超限时必须告警并降级（4.8.6）。

**并发模型与异步模型是两件事（硬性约束）**

本产品的吞吐来自**进程数**，不来自事件循环。任何以"改成异步就能提速"为由的方案，直接否决。

| 模块                          | 密集类型           | 并发手段                    |
| --------------------------- | -------------- | ----------------------- |
| 解析、L1 校验、T1 后处理             | **CPU**        | **进程池**（不可用事件循环、不可用线程池） |
| 上传 / 下载 / 进度查询 API          | IO             | 异步（事件循环）                |
| 队列消费                        | IO + CPU       | 异步取消息 → 派给进程池执行         |
| 对象存储读写、数据库写入                | IO             | 同步（每批一次，不在关键路径）         |
| **调外部增强器（OCR / VLM / LLM）** | **IO，单次等待数十秒** | **小并发池，默认上限 4，可配置**     |

依据：1 核 @ 15ms/页 ≈ 66 页/秒，16 核 ≈ 1000 页/秒。把 CPU 密集链路改成异步，吞吐仍是 66 页/秒，只增加复杂度，直接违反 6.1 的吞吐目标。

> 补充事实：`process_pdf_with_ocr` 会释放 GIL，多线程**确实**能并行。但仍必须用进程池——Rust 扩展一旦栈溢出或 panic 会终止整个进程，`try/except` 与线程池都无法接住（4.8.5）。

**三条可测要求**

| # | 要求                                                               | 验收方式                                  |
| - | ---------------------------------------------------------------- | ------------------------------------- |
| 1 | 一切外部依赖调用（对象存储、队列、外部增强器、LLM）**必须设并发上限与超时**，默认上限可配置，不得无限放行         | 注入 200 个待调外部增强器的任务，观测并发峰值 ≤ 配置值，超时有告警 |
| 2 | API 层支持 **≥200 并发状态查询，P95 < 200ms**                              | 压测脚本，200 并发持续 60s                     |
| 3 | 长任务进度**不得依赖进程内状态**（`asyncio.Task` / 线程字典 / 内存 future 均禁止作为唯一状态源） | 处理中途 kill -9 主进程，重启后进度从库中恢复且不丢已完成批    |

> 第 3 条常被误解为"异步就能保证长任务可靠"。**异步不提供持久性**，持久性来自 4.8.5 的落盘分层（PG 状态 + 对象存储产物 + 队列），三者缺一不可。

### 4.4 质量管控模块

#### 4.4.1 功能概述

建立**四层质检体系**。核心原则：**便宜的全量逐页，昂贵的分层抽样，业务的全量，人工的例外**。

#### 4.4.2 四层模型

```
L1  逐页确定性指标     全量 · ms 级 · 硬门控 · 定位到页
L2  逐页昂贵校验       分层抽样 + 低质量页 100%
L3  文档级聚合         全量 · 业务勾稽 · 安全网
L4  人工               仅升级
```

**为什么 L1 必须全量**：便宜且是唯一能定位"哪一页"的手段。没有页级定位，修复只能整本重跑。

**为什么 L2 必须抽样**：往返校验 50–500ms/页，全量等于全量 OCR，成本优势归零。

#### 4.4.3 L1：逐页确定性指标（全量，硬门控）

| 指标                    | 定义                                                                     | 抓什么问题     | 成本    |
| --------------------- | ---------------------------------------------------------------------- | --------- | ----- |
| `char_density`        | 抽取字符数 / 文本区域面积                                                         | 空白页、大面积漏抽 | O(1)  |
| `glyph_coverage`      | ToUnicode 成功映射字形 / 总字形（由 `cmap_gaps` 直接算：`(codes - unmapped) / codes`） | 编码损坏、乱码   | 抽取时顺带 |
| `cid_unmapped_ratio`  | 未映射 CID 占比                                                             | 同上，更敏感    | 顺带    |
| `empty_region_ratio`  | 空白块面积 / 页面面积                                                           | 版式识别失败    | 低     |
| `table_cell_fill`     | 非空单元格 / 总单元格（仅 T1 补齐 cell 后可用）                                         | 表格结构错     | 低     |
| `row_col_consistency` | 每行列数方差                                                                 | 表格断裂/错位   | 低     |
| `reading_order_score` | y 单调性 + 列切换惩罚                                                          | 分栏错序      | 低     |
| `bbox_coverage`       | 有坐标文本 / 总文本                                                            | 坐标缺失      | 低     |
| `header_footer_leak`  | 页眉页脚进入正文比例                                                             | 污染正文      | 低     |
| `page_number_ok`      | 页码存在且连续                                                                | 缺页/错序     | 低     |

**`extract_quality` 是上表的加权合成，不是第 11 个指标。** 它把上述可量化指标压成一个页级 0–1 分数，作为兜底档位判定与抽样分层的输入。权重由黄金集拟合，不得拍脑袋（见 4.4.7）。

**硬门控（任一不过 → 该页 fail）：**

```
glyph_coverage      > 0.95
cid_unmapped_ratio  < 0.01
empty_region_ratio  < 0.30
table_cell_fill     > 0.90        （仅表格页，且仅 T1 补齐 cell 后）
page_number_ok      == true
char_density        > 阈值（按页型分档）
```

> 阈值起点值，最终以 4.4.7 标定结果为准。

#### 4.4.4 L2：昂贵校验（分层抽样）

| 手段               | 做法                                                                                            | 抓什么              | 成本         |
| ---------------- | --------------------------------------------------------------------------------------------- | ---------------- | ---------- |
| **往返校验**         | 页面 render → OCR/VLM → 与抽取文本比 CER                                                              | 文本层本身错误、乱码       | 50–500ms/页 |
| **跨引擎一致性**       | `engine.pdf` ↔ `engine.pdfshift`（pdftotext/pdfminer/PyMuPDF 封装成的对照插件），比 CER + 表格 cell overlap | 抽取实现差异导致漏字       | ~100ms/页   |
| **VLM-as-Judge** | 页面图 + Markdown 一起给 VLM，要求列出不一致                                                                | 语义、结构、数值错误，且产出归因 | 1–3s/页     |

**扫描件特例**：无文本层时往返退化为"OCR vs OCR"，无意义。扫描件改用：OCR 置信度 + 语言模型困惑度 + 业务勾稽 + 抽样人工。

#### 4.4.5 抽样策略（分层，非随机）

| 页类型                           | 抽样比例       | 理由            |
| ----------------------------- | ---------- | ------------- |
| `extract_quality < 0.85` 的页   | **100%**   | 页级已知风险，全查     |
| `class_confidence < 0.85` 的文档 | **整本转 T3** | 判不准是什么类型，抽页没用 |
| 表格页                           | 20–30%     | 结构最易错         |
| 跨页边界页（表续、章末）                  | 100%       | 合并最易出错        |
| 首页 / 末页                       | 100%       | 业务价值高         |
| 普通文本页                         | 5–10%      | 便宜、量大         |

**约束**：每文档至少 5 页、至多 20 页；抽样用于**估计文档级质量**，不用于判定单页。

#### 4.4.6 门控与评分

**四维还原度：**

| 维度   | 度量              | 简单页：原生 / 含 T1        | 中等页：原生 / 含 T1        |
| ---- | --------------- | -------------------- | -------------------- |
| 文本还原 | CER             | ≤ 2%                 | ≤ 5%                 |
| 结构还原 | 阅读顺序一致率         | ≥ 92% / ≥ 95%        | ≥ 88% / ≥ 90%        |
| 结构还原 | TEDS            | ≥ 0.80 / ≥ 0.85      | ≥ 0.72 / ≥ 0.75      |
| 结构还原 | 标题层级准确率         | ≥ 0.78（仅 tagged PDF） | ≥ 0.70（仅 tagged PDF） |
| 语义还原 | 字段级 exact match | ≥ 98%                | ≥ 95%                |
| 版式还原 | bbox IoU        | ≥ 0.90               | ≥ 0.80               |

> **为什么拆"原生 / 含 T1"两组**：插件自测基线为 TEDS 0.814、标题 0.788、阅读顺序 0.915。若直接要求 TEDS ≥ 0.85，等于要求超过插件自身能力上限，上线即不达标。拆成"原生基线"与"含 T1 后处理目标"两级，才能既反映真实能力、又给自建部分定出明确增量责任。

**综合分：**

```
fidelity = w1·(1-CER) + w2·TEDS + w3·semantic_match + w4·layout_iou
Σw = 1，权重由黄金集拟合，不得拍脑袋
```

**门控：**

- 硬门控：L1 全过，否则直接 fail，不进 L2（省钱）
- 软门控：`fidelity ≥ τ`，τ 按文档类型/复杂度分档

#### 4.4.7 标定流程（可验收的关键）

1. 建 **200 页黄金集**，人工按 4 维打分（0–3 分）。覆盖：纯文本页、单表页、跨页表、多栏页、扫描页、编码损坏页，各不少于 20 页。
2. 跑指标 → 拟合权重，使 `fidelity` 与人工总分的 **Spearman 相关 > 0.8**。
3. 扫阈值，画 **STP 率 vs 误放率** 曲线，选工作点（目标 STP 80%、误放 < 2%）。
4. **单独标定 `extract_quality`**：使其与人工判定的"该页是否需要人工介入"一致率 ≥ 0.85。这项标定决定 T1/T2 触发是否准确。
5. 上线后每月抽 100 页人工复核，**漂移告警**。

#### 4.4.8 质检器（QC）输出契约

```json
{
  "verdict": "pass | fail | uncertain",
  "extract_quality": 0.62,
  "fidelity": 0.93,
  "defects": [
    {
      "code": "table_row_inconsistent",
      "location": {"type": "table", "index": 2, "bbox": [120, 340, 520, 610]},
      "evidence": {"row_counts": [5, 5, 3, 5], "variance": 1.2},
      "severity": 0.8,
      "suggested_action": "rebuild_table_cells"
    },
    {
      "code": "encoding_loss",
      "location": {"type": "page", "page_no": 82},
      "evidence": {"glyph_coverage": 0.31, "unmapped": 1240},
      "severity": 0.95,
      "suggested_action": "ocr_page"
    }
  ],
  "attribution": "table_structure",
  "recommended_action": "resegment_table",
  "qc_confidence": 0.88
}
```

**要求**：

1. 必须是结构化字段，禁止自由文本；QC 只读，不得修改产物。
2. **`defects[]` 是本契约的核心，`verdict` 只是它的结论。** 只有分数没有缺陷清单，等于"知道这页不好但不知道哪儿不好"，只能整页重做——而整页重做对确定性函数毫无意义（4.5.1）。
3. **每条缺陷必须带 `location`**，且精确到可操作粒度（表格序号 + bbox / 页码 + 区域）。**没有 `location` 的缺陷视为不可修复，必须拒绝入库。**
4. `defects[].code` 取自 4.5.7 的封闭集，不得自造。

> 注：此处 `qc_confidence` 是 **QC 对自身判定的置信度**，与被评估页面的 `extract_quality` 不是同一个东西，不得混用。

#### 4.4.9 裁判也要考试

QC 自身需在黄金集上评测：precision ≥ 0.95、recall ≥ 0.90。否则"它说 pass"不可信。

#### 4.4.10 业务规则校验

- 校验类型：字段存在性、格式、数值范围、逻辑关系（勾稽）
- 规则以 RulePack 形式管理（见 4.6）
- 支持规则优先级与异常等级
- 输出不通过项、位置、等级

#### 4.4.11 校验成本分层与"不可跳过简单页"

**问题**：L1 全量会不会拖慢整体？"纯文字页看起来很简单，能不能不校验？"

**答**：按成本的三个层级拆开看，就不存在这个取舍。

| 层              | 内容                                                         | 单页成本                | 怎么来                         |
| -------------- | ---------------------------------------------------------- | ------------------- | --------------------------- |
| **A 免费信号**     | 字符数、替换符/`.notdef` 计数、unmapped glyph 计数、有坐标项占比、零宽/超宽字符、文字密度 | **≈ 0**             | 解析器本就在遍历每个 text item，只增加计数器 |
| **B 需遍历的结构检查** | 表格行列一致性、空白区面积比、块序检查、跨页表边界                                  | 1–3 ms（表格页 5–10 ms） | 需对 `text_items` 做一次空间聚类     |
| **C 抽样校验（L2）** | 往返 OCR / 跨引擎 / VLM                                         | 100–300 ms          | 需渲染 + 模型                    |

- **A 层 100% 执行**，它不是"多做一遍"，是解析过程的副产物。
- **B 层按信号触发**：由插件免费给出的 `pages_with_tables`、`columns > 1`、A 层异常三者决定。无表格、单栏、A 层干净的页跳过 B 层。
- **C 层按 4.4.5 抽样**。

**禁止"跳过简单页"，两个理由**

1. **判断"这页简单"的成本约等于判断"这页合格"的成本。** 要判简单得看有没有表格、是否单栏、字形映射是否正常、密度是否合理——四项里三项就是 A 层信号。为了决定"要不要校验"已经把校验要的信息算完了，剩下 B 层只占 1–3 ms。
2. **纯文字页恰恰是失败高发区。**

| 缺陷                            | 高发页型     |
| ----------------------------- | -------- |
| 编码损坏（CJK 字体无 ToUnicode，输出替换符） | **纯文字页** |
| 双栏串行（两栏被读成交替的行）               | **纯文字页** |
| 页眉页脚/页码混入正文                   | **纯文字页** |
| 脚注被插入段落中间                     | **纯文字页** |
| 表格错行、跨页断裂                     | 表格页      |

表格页出问题大家都会盯；但真正把整份文档搞废的是编码与分栏，它们全发生在"看起来最简单"的纯文字页上。**跳过纯文字页等于专门跳过漏检率最高的一类。**

**时间账（200 页文档）**

| 项                    | 耗时      | 占比   |
| -------------------- | ------- | ---- |
| 解析（200 × 15 ms）      | ~3.0 s  | —    |
| A 层                  | ~0      | 0%   |
| B 层（约 40% 的页触发）      | ~0.15 s | 2–3% |
| L2 抽样（15 页 × 100 ms） | ~1.5 s  | 25%  |
| 合并与输出                | ~0.5 s  | 8%   |

跳过 80% 的简单页，省约 0.1 s，占任务总时长 1.7%，而代价是 **STP 率的分母变成"我们愿意检查的页"，这个指标对外不可解释**。且该开销不占用关键路径：1000 份 × 200 页的校验总 CPU 为 150 s，16 worker 摊开约 10 s，相对 30–60 分钟总时长可忽略。

#### 4.4.12 性能档位与削减顺序

**唯一合法的削减顺序（从最贵的一层往下削）**

```
① L2 抽样比例        15 页/文档 → 5 页 → 首末页 + fail 页        省 0.75 s
② 增强轮次           单页 3 轮 → 2 轮；单文档重跑页上限 20% → 10%   省 0.3–1 s
③ 增强档位           禁 T3 换引擎，只保留 T1/T2                    省 1–5 s
④ L1 / A 层 / B 层   —— 永不削减
```

**三档位（`profile_speed`，4.1.4）**

| 档位            | L1     | L2 抽样               | 增强       | 代价                             |
| ------------- | ------ | ------------------- | -------- | ------------------------------ |
| `quality`（默认） | 全量     | 15 页/文档，fail 页 100% | 3 轮，含 T3 | —                              |
| `balanced`    | 全量     | 5 页/文档，fail 页 100%  | 2 轮，含 T3 | 空洞率略升                          |
| `fast`        | **全量** | fail 页 + 首末页        | 仅 T1/T2  | **STP 率降级为估算值，报告必须标注"不可用于验收"** |

**三档的 L1 都是全量。** L1 决定"哪几页有问题"，一旦不全量，后续修复、标记、报告全部失去依据——省下 2% 换来 100% 的报告不可信，这笔交易永远不划算。

### 4.5 异常处理与修复模块

#### 4.5.1 功能概述

**不是重试，是带预算的动作搜索。** 确定性解析器重跑结果不变，因此每次修复必须改变"输入 / 参数 / 算子 / 后处理方式"四者之一（见 4.5.8）。

兜底分四档（T0–T3，见 4.3.5），本节定义每档可执行的具体动作。

#### 4.5.2 失败分类法（封闭集）

| 大类      | 子类                | 典型特征        |
| ------- | ----------------- | ----------- |
| **技术类** | `encoding_broken` | CID 未映射、乱码  |
|         | `table_break`     | 行列不一致、单元格缺失 |
|         | `reading_order`   | 分栏错序        |
|         | `low_density`     | 空白页、大面积缺失   |
|         | `rotation`        | 页面旋转/倾斜     |
|         | `scan_noise`      | OCR 噪声      |
| **业务类** | `field_missing`   | 必填字段缺失      |
|         | `value_mismatch`  | 勾稽不平        |
|         | `format_invalid`  | 格式不符        |
|         | `rule_conflict`   | 规则冲突        |

> 归因输出必须是上表中的一个 label + 置信度，禁止自由文本。

#### 4.5.3 修复动作空间

| 动作                          | 档位 | 触发条件               | 效果                                          | 成本 |
| --------------------------- | -- | ------------------ | ------------------------------------------- | -- |
| A `switch_engine`           | T3 | 归因=插件能力不足          | 换更强 parser 插件                               | 中  |
| B `tune_params`             | T2 | 归因=参数不当            | 分栏阈值 / 表格模式 / 粗体判定 / 页范围重跑                  | 低  |
| C `transform_input`         | T3 | 归因=图像质量            | 旋转 / 去斜 / 裁边 / 超分                           | 中  |
| D `resegment`               | T1 | 归因=结构错             | 段落重排、跨页表合并                                  | 低  |
| E `ocr_fallback`            | T3 | 归因=文本层缺失/损坏        | 该页转 OCR/VLM 插件                              | 高  |
| F `escalate`                | T3 | 预算耗尽 / 无法判定        | 进人工 + 诊断卡                                   | 人工 |
| **H `strip_header_footer`** | T1 | 归因=正文被页眉页脚污染       | 按页框位置与重复模式剔除                                | 极低 |
| **I `rebuild_table_cells`** | T1 | 归因=插件只出 Markdown 表 | 基于 `text_items` 的 bbox 重算行列、合并单元格、补 cell 坐标 | 低  |

**T1 动作（D / H / I）是 P0 的重点自建内容**，也是最划算的兜底手段：纯 CPU、毫秒级、不需要重跑或换引擎。

#### 4.5.4 预算与收敛

| 规则       | 值                                           |
| -------- | ------------------------------------------- |
| 单页最大尝试次数 | 3                                           |
| 单文档最大成本  | 按 TaskSpec 配置，默认 ¥0.5                       |
| 单文档最大耗时  | 默认 600s                                     |
| **动作消耗** | T1 = 0，T2 = 1，T3 = 2                        |
| 无进展检测    | 指标提升 < 5%，或缺陷数未减少 → 该算子判无效（见 4.5.9）         |
| 动作去重     | 同一页同一缺陷码只允许修一次                              |
| 算子无变化    | `OperatorResult.changed == false` 立即判无效，不重试 |
| 终止       | 任一预算触发即升级，不允许无限循环                           |

**说明**：T1 动作为纯后处理、毫秒级，若也计入预算，会导致"能靠后处理解决的小问题被提前升级到人工"。因此 T1 不计消耗，但**每个 T1 动作在同一页只能用一次**（靠动作去重约束），避免死循环。

#### 4.5.5 诊断卡（人工升级产物）

必须包含：失败页缩略图、L1 指标、当时的路由 `reason` 与 `profile_snapshot`、已尝试动作、归因结果、建议动作、关联规则、历史相似案例。

#### 4.5.6 人工介入

- 待办队列，支持按优先级/业务域/异常等级排序
- 支持查看详情、手动修正、重新触发
- 支持标记最终失败并关闭
- **人工修正结果回流黄金集**（用于持续标定），但不自动改规则
- P0/P1 阶段待办队列以 API + 清单文件形式提供，图形化归 P2（见 8.3）

#### 4.5.7 缺陷码封闭集（驱动修复的唯一入口）

**4.5.2 的失败分类法回答"哪一类失败"，本节回答"具体是哪里坏了"。** 前者用于统计与归因训练，后者用于驱动修复。二者必须分开：分类法可以粗，缺陷码必须细到能定位。

| #  | 缺陷码                      | 判定条件                                                  | `location` 必填字段                    | 默认算子                          | 档位      |
| -- | ------------------------ | ----------------------------------------------------- | ---------------------------------- | ----------------------------- | ------- |
| 1  | `encoding_loss`          | `glyph_coverage < 0.95` 或 `cid_unmapped_ratio > 0.01` | `page_no`（可带 `bbox` 限定区域）          | `ocr_page`                    | T3      |
| 2  | `low_density`            | `char_density < 页型阈值`                                 | `page_no`                          | `ocr_page` / `extract_region` | T3 / T2 |
| 3  | `region_empty`           | 某文本块面积 > 5% 页面且字符数 ≈ 0                                | `page_no` + `bbox`                 | `extract_region`（定点补抽）        | T2      |
| 4  | `table_structure_broken` | 表格行数方差 > 0、列数不一致，或 `md` 有表但 `cells` 为空                | `page_no` + `table_index` + `bbox` | `rebuild_table_cells`         | T1      |
| 5  | `table_cross_page_break` | 相邻页表头列名相似度 > 0.8 且表体触页边界                              | `page_no`（起始页）+ `table_index`      | `merge_cross_page_table`      | T1      |
| 6  | `reading_order_broken`   | `reading_order_score < 0.88`                          | `page_no` + `item_range`           | `reorder_blocks`              | T1      |
| 7  | `column_mixed`           | `columns > 1` 且同一行内 bbox 跨栏                           | `page_no` + `bbox`                 | `resegment_columns`           | T2      |
| 8  | `header_footer_leak`     | `header_footer_ratio > 0.05`                          | `page_no` + `bbox`                 | `strip_header_footer`         | T1      |
| 9  | `page_rotated`           | `/Rotate` 非 0，或文本基线倾角 > 2°                            | `page_no` + `angle`                | `rotate_page` / `deskew`      | T2 / T3 |
| 10 | `page_number_broken`     | 页码缺失或序列不连续                                            | `page_no`                          | **无**（仅文档级标记）                 | —       |
| 11 | `plugin_reason_unknown`  | 上游返回的 `ocr_reason` 未出现在映射表中                           | `page_no` + `raw_reason`（原样保留）     | **无**（记录 + 计数，交人工）            | —       |

**四条硬性要求**

1. **缺陷码是封闭集**，与 4.5.2 的失败分类法一样，不得由模型自由生成。新增码必须走版本升级。
2. **码 → 算子的映射写死在代码里**，不允许运行时推断。这样"同一缺陷两次修复走了不同算子"就不可能发生。
3. **每条缺陷必须带 `location` 且可操作**。缺 `location` 的缺陷不得进入修复队列，只能计入统计。
4. **第 10 项不设修复算子**：页码不连续通常是原文档问题（装订、扫描缺页），修复它等于篡改证据。文档级标记 + 报告中说明，是唯一正确处理。

**上游插件原因码的接入规则（复用而非重造）**

插件返回的 `ocr_reason` / `ocr_reasons_by_page` 已经是**逐页、机器可读的失败原因**，等于上游替我们做了半套归因。接入规则如下：

> **先分清两张映射表，别混为一谈**：
>
> - `reason → defect_code`（上游开放集 → 本系统封闭集）= **配置，可随插件版本变更**（本节）
> - `defect_code → operator`（本系统封闭集 → 本系统算子）= **代码，写死**（上方硬性要求 2）
>
> 前者必须可配，因为输入集合不由我们控制；后者必须写死，因为输出行为必须可复现。两张表的可变性相反，这正是"封闭集"与"开放集"的直接后果。

| # | 规则                                                                  | 说明                                                                                               |
| - | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 1 | **映射表放配置，不放代码**                                                     | 形如 `{plugin: engine.pdf, version: 1.x, reason: <上游串> → defect_code}`。禁止在代码里 `if reason == "..."` |
| 2 | **未知 reason 一律落到第 11 项 `plugin_reason_unknown`**，并原样记录 `raw_reason` | 不得丢弃、不得凭猜测归入邻近码。丢了原因，人工拿到的就是"原因未知"                                                               |
| 3 | **映射表按插件版本分组**                                                      | 上游升级后新增的 reason 自动落入未知桶，报告里能立刻看出"这是升级带来的"，而不是悄悄改变统计口径                                            |
| 4 | **`plugin_reason_unknown` 的计数进运营指标**（4.9）                           | 单次任务中该码占比 > 5% 时告警：大概率是插件升级或映射表过期，属于可运营问题，不是数据问题                                                 |
| 5 | **映射只做一次，单向**                                                       | `defect_code` 不反推 `reason`。报告里两个字段并列展示（一个是上游证据、一个是本系统判定）                                         |

**为什么这条值得单列**：它决定了"你是在复用上游能力，还是在重造一遍"。没有这张映射表，插件的逐页判定结果进了系统就被丢弃，报告只能写"该页解析失败"；有了它，报告可以写"该页无文本层，上游已标记，已转 OCR"，而这个信息是零成本拿到的。三类能力的复用边界见 4.3.5 与 4.3.3。

#### 4.5.8 增强算子四分类（"重试"的正确含义）

**前提事实：解析插件是纯函数**——同样的 bytes、同样的参数，输出永远一致。因此在本系统里：

> **"重试"不存在。存在的只有"换一个操作"。**

只有四个方向可换，必须穷举清楚：

| 类别        | 改什么                                     | 是否重调解析插件    | 典型缺陷                | 预算 |
| --------- | --------------------------------------- | ----------- | ------------------- | -- |
| **① 后处理** | 用已有 `text_items` 的坐标重算                  | **不调**      | 表格结构、跨页断裂、页眉页脚、阅读顺序 | 0  |
| **② 换输入** | 旋转、裁边、分栏切分、区域限定                         | 调，但**输入变了** | 页面旋转、双栏串行、局部漏抽      | 1  |
| **③ 换参数** | `pages` / `bold_from_weight` / 阈值 / 页范围 | 调，**参数变了**  | 粗体判定、标题层级           | 1  |
| **④ 换算子** | 换对照引擎、换 OCR/VLM                         | 调**别的插件**   | 编码全损、扫描件、整页无文本层     | 2  |

**必须诚实面对的约束**：该插件对外暴露的可调参数极少——实际只有 `pages`、`bold_from_weight`、`bold_weight_threshold`、`model_directory`、`offline`、`render_dpi`。**表格检测模式、分栏阈值都没有暴露成参数。**

因此：

- **类别 ③ 基本不能依赖。** 指望"调个参数再跑一次"来解决表格或分栏问题，在实现上是走不通的。
- **主力必须是类别 ①。** 缺陷码里有五个（表格结构、跨页、页眉页脚、阅读顺序、表格跨页）根本不需要重调插件。
- **类别 ②④ 是真正的兜底**，成本显著高于 ①。

> 这正解释了为什么必须自建增强层：**插件给不了调整空间，只能在外面改输入、换算子。**

**算子签名（从第一天统一，P1 抽成插件时不用改调用方）**

```
operator(artifact, defect, ctx) -> OperatorResult
  candidate : 新产物候选（None 表示放弃）
  changed   : 是否产生实际变化        ← 停机机制的核心依据
  cost      : 预算消耗（T1 类固定为 0）
  notes     : 诊断备注
```

**两条硬约束**

1. **算子必须幂等**：同输入跑两次结果一致。
2. **算子不得修改原产物**，必须返回新对象。否则重跑会污染已有产物，续跑不安全（4.8.5）。

**形态要求（P0）**：算子是一组**同进程纯函数 + 一张映射表 + 一个调度器**，不做成独立插件进程。理由是它们是每页可能被调用 2–3 次的高频操作，跨进程序列化开销（见 4.3.7）远大于算子本身的毫秒级计算。等某个算子真的需要独立部署（要 GPU、要独立升级、按客户定制），再按 5.1 契约抽出，签名不变。

#### 4.5.9 增强回路与停机条件

**单页增强回路**

```
PageArtifact + defects[]
        ↓
  取第一条未处理的缺陷
        ↓
  查映射表 → 算子
        ↓
  执行 → OperatorResult
        ↓
  changed == false ? ──是──→ 该算子无效，标记"此路不通"，不再重试
        ↓ 否
  质检复检（只算该缺陷相关指标）
        ↓
  指标提升 ≥ 5% ? ──否──→ 丢弃候选，该算子判无效
        ↓ 是
  采纳候选 → defects 重算
        ↓
  仍有缺陷且预算未尽 → 回顶部
```

**三层预算 + 两条收敛约束**

| 类型       | 条件                                      | 触发后             |
| -------- | --------------------------------------- | --------------- |
| 次数       | 单页最多 3 轮增强                              | 归复杂页            |
| 时间       | 单页累计 ≤ 2 s                              | 归复杂页            |
| 成本       | 按 4.5.4 的档位扣减                           | 归复杂页            |
| **无进展**  | 新一轮 `extract_quality` 提升 < 0.05，或缺陷数未减少 | **该算子判无效，不再尝试** |
| **同码唯一** | **同一缺陷码在同一页只修一次**                       | 修不动直接升级，不换花样    |

**"同码唯一"是最关键的一条。** 没有它会陷入循环：表格重建失败 → 试换参数 → 仍失败 → 试裁边 → 仍失败 → 回头再试表格重建，看着只试了 3 次，实际原地转圈。

**采纳规则**：候选产物必须带来**可量化的指标提升**才被采纳。不接受"看起来好一些"。这是防止增强层自己变成不确定来源的唯一手段。

**归复杂页之后不许再动**：写一条 `PageGap` 记录（4.5.10），交给批量增强包或人工。批处理里一个坏页多耗 10 s，1000 份文件就是 3 小时——这比"这页没解析好"严重得多。

#### 4.5.10 复杂页收口（散落的失败页怎么处理）

**核心结论：失败页是离散的，但二次处理必须打包。**

四步，缺一不可：

| 步             | 做什么                                                                                                              | 输出                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| **1. 页级标记**   | 每个失败页写 `PageGap`：`doc_id, page_no, defect_codes[], evidence, tried_operators[], recommended_tier, fallback_used` | `PageGap` 记录（精确到页，这是"散落"能被追踪的前提） |
| **2. 抽子集**    | 用 `pages=[...]` 只抽失败页，生成**只含失败页的临时 PDF**，同时生成页码映射表（临时第 3 页 = 原文件第 82 页）                                          | 临时文件 + 映射表                       |
| **3. 聚包批量增强** | 跨文档的失败页按 50–100 页聚成一包，送外部增强器（OCR/VLM/MinerU）批量跑                                                                  | 每包一次调用                           |
| **4. 页码回填**   | 增强结果带 `(doc_id, 原页码)`，合并时替换对应页产物，档位由 T3 降回"已修复"                                                                  | 回填后的 artifact                    |

**第 3 步是成本关键**：2000 个散落在 1000 份文件里的失败页 → 聚成 20 个包 → **20 次调用，而不是 2000 次**。

**两条约束**

- **不重跑整个文件**。只抽失败页，其他页的产物完全不动。
- **页码映射表必须落盘并参与幂等键**，否则回填错位会导致整份文档页码错乱，比解析失败更严重。

#### 4.5.11 外部增强器不可用时的降级路径

按成本从低到高，三条：

| 降级          | 做法                                             | 效果            | 何时用            |
| ----------- | ---------------------------------------------- | ------------- | -------------- |
| `local_ocr` | 本地 render + PP-OCR                             | 文字能救回，复杂表格救不回 | **默认档**        |
| `mark_only` | 不处理，输出写明"第 37、82、155 页未还原，原因：跨页表断裂"，附缩略图，进人工队列 | 诚实的最低档        | 无 OCR 运行时      |
| `fail_doc`  | 整份不出                                           | 最差            | 仅客户明确要求"不全不出"时 |

**要求**：

1. **`fallback.enhancer` 必须是配置项**（4.1.4），不得写死。
2. **`mark_only` 是合法的交付结果，不是失败**。批处理场景里，95% 内容 + 5% 精确标记，远优于整份不出。
3. **报告必须显式声明用了哪条降级路径**，且 `mark_only` 的结果在报告中标注"不可用于自动化下游"。
4. **外部增强器不是第一级，是最后一级**（见 4.5.8）：一上来就用它，等于放弃全部成本优势，变成与 Docling / MinerU 正面竞争解析精度，那是另一门生意。

### 4.6 个性化规则配置模块

#### 4.6.1 功能概述

个性化 = **数据**，不是代码。三层分离：

| 层            | 形态            | 谁能改     | 变化频率 |
| ------------ | ------------- | ------- | ---- |
| 机制 Mechanism | 代码（只读、版本化）    | 研发，发版   | 极低   |
| 策略 Policy    | 数据（YAML/JSON） | 交付 / 客户 | 高    |
| 决策 Decision  | 模型            | Agent   | 中    |

#### 4.6.2 RulePack（声明式规则包）

```yaml
rulepack: cn_a_share_annual_v1
extends: base.financial_report
fields:
  - id: revenue
    label: 营业收入
    type: money
    anchors: ["营业收入", "营业总收入"]
    required: true
checks:
  - id: balance_identity
    type: expression
    expr: "total_assets == total_liabilities + total_equity"
    tolerance: 0.001
  - id: page_number_sequence
    type: sequence
thresholds:
  extract_quality_min: 0.85
  doc_stp_target: 0.90
```

**约束**：

- `type: expression` 使用**受限表达式引擎**（JSONLogic / CEL / expr），只允许白名单字段与白名单函数
- 无副作用、可静态分析、可沙箱求值
- 禁止在 RulePack 中嵌入任意代码

#### 4.6.3 自然语言 → RulePack（Agent 编译链路）

```
用户自然语言
  → 大模型生成 RulePack 草案
  → JSON Schema 校验
  → dry-run（在 3 篇样本上跑，出报告）
  → 人类可读摘要 + diff
  → 人工确认
      ├─ 否 → 错误回灌，重试（≤ 2 次）
      └─ 是 → 冻结版本 → 生效
```

**要求**：

- 编译期用大模型，运行期用确定性
- 每条规则必须可追溯到原始需求文本
- 冲突检测：新规则与已有规则矛盾时阻断
- 回滚：任意历史版本一键回滚

**同一编译链路也用于生成 `scope.page_filter`**（4.1.4）：用户说"这批年报只处理带表格的页，目录页跳过" → 编译为 `page_filter` → schema 校验 → dry-run → 确认。

#### 4.6.4 扩展能力（替代"上传自定义脚本"）

| 方式        | 形态                                               | 边界                       |
| --------- | ------------------------------------------------ | ------------------------ |
| 声明式规则     | RulePack                                         | 覆盖 90% 需求                |
| 扩展插件      | 独立插件包（engine / validator / extractor / exporter） | 注册、版本化、灰度、可下线            |
| 沙箱代码（仅内部） | 研发侧长尾工具                                          | 只读输入、候选产物、同一校验门、无网络、资源限额 |

**用户侧永远不能写代码，只能写数据。**

#### 4.6.5 变更影响分析

- 规则变更后，可选择：仅新任务生效 / 对历史数据重跑
- 重跑需评估成本，给出预估页数与费用
- 重跑结果与历史结果可 diff

#### 4.6.6 个性化字段提取（三层，不做成 Agent）

字段提取的本质是"**找锚点 → 定位 → 抽值 → 校验**"，规则可覆盖约 90%，不需要模型主导。

| 层           | 做法                                 | 适用          | 阶段     |
| ----------- | ---------------------------------- | ----------- | ------ |
| **① 声明式字段** | 锚点词、类型、正则、所在区域（正文/表格/页眉）、是否必填、是否可空 | 版式有规律、字段名稳定 | **P0** |
| **② 模板提取**  | 固定版式按坐标区域抽（如财报三表），比文本锚点稳           | 同一客户反复出现的版式 | P1     |
| **③ 模型抽取**  | 仅在①②失败时兜底，输出必须过 JSON Schema 校验     | 长尾版式        | P2     |

**约束**

1. 三层**逐级降级**，不是并列可选。能用①就不用②，能用②就不用③。
2. **禁止"让大模型直接读 Markdown 自由抽字段"**。不可复现、成本高、无法审计。
3. ③ 的结果必须标记 `extraction_source: model`，报告中单独统计其占比；该占比是"规则覆盖不足"的直接指标。
4. 字段级校验（类型、范围、勾稽）在**三层之外统一做一次**，不因抽取方式不同而不同——否则同一字段两套标准。

**插件类型缺口（V2.2 修正）**

|                        |           |           |                                                                                                  |
| ---------------------- | --------- | --------- | ------------------------------------------------------------------------------------------------ |
| 5.1 的插件类型枚举原为 \`engine | validator | connector | exporter`，**缺 `extractor`**，导致字段提取器无法按插件契约挂载。V2.2 补入 `extractor\` 类型，允许客户自带提取器插件，但其输出仍必须过上述统一校验。 |

### 4.7 合并与输出模块

#### 4.7.1 合并流程

```
页级 artifact → 按页码排序（跨批按 page_no 重排）
            → 跨页表合并（表头识别 + 列对齐）
            → 目录/章节重建（heading 层级）
            → L3 文档级校验
            → 输出
```

**跨页表合并是自建能力**：插件只按页输出 Markdown 表格，不提供跨页续接。合并依据为相邻页表头的列名相似度 + 列数一致性 + 表格 bbox 与页边距的关系。

#### 4.7.2 局部降级

- 单页失败不阻塞整篇
- 标记 gap，输出带 per-section `extract_quality`
- 文档报告写明："第 37 页表格未还原，`extract_quality` 0.4，已转人工"

#### 4.7.3 输出格式

| 格式          | 用途                  |
| ----------- | ------------------- |
| JSON        | 系统集成，带完整 provenance |
| CSV / Excel | 业务人员使用              |
| Markdown    | 可读文本，供 RAG/检索       |
| 数据库写入       | 归集入库                |
| 处理报告        | 质量、成本、异常汇总          |

#### 4.7.4 分级交付（不是开关，是三档）

**质量合并不做成"达标输出 / 不达标不输出"。** 批处理场景里整份不出是最差体验——用户宁要 95% 内容 + 5% 明确标记，也不要一份空报告。

| gap 页占比    | 交付等级                | 处理                   | 报告标注     |
| ---------- | ------------------- | -------------------- | -------- |
| 0          | `complete`          | 正常输出                 | 无        |
| 0 < x ≤ 5% | `partial_with_gaps` | 照常输出，产物内嵌 gap 标记     | 列出 gap 页 |
| > 5%       | `needs_review`      | 输出（带空洞）+ **强制进人工队列** | 显著标注风险   |

**三条硬性要求**

1. **gap 页必须保留占位，不得跳过。** 否则页码全部错乱，下游按页码取数全废。这一条比"内容完整"更重要。
2. **gap 标记必须内嵌在产物里**（Markdown 用可识别的标记块，JSON 用 `gap: true` 字段），不能只写在报告里——下游拿到产物时可能看不到报告。
3. **`gap_tolerance` 可由 TaskSpec 配置**（4.1.4），但**不允许配置成"gap 页可删除"**。

#### 4.7.5 报告分层（千份文件不爆炸）

1000 份文件如果逐份出明细，报告会变成几万行的巨型文档，没人看。**分层，且不预生成明细。**

| 层       | 内容                                                 | 体量           |
| ------- | -------------------------------------------------- | ------------ |
| ① 任务总览  | 总数、成功率、gap 页总数、成本、耗时、Top 失败原因                      | 10 个数字，一页    |
| ② 按原因聚合 | 不看文件看模式："编码损坏 23 个文件 / 156 页"、"表格跨页 41 个文件 / 89 页" | ≤ 10 行       |
| ③ 文件清单  | 每文件一行：ID、页数、gap 页数、状态。可排序可筛                        | 1000 行，但只是索引 |
| ④ 单文件详情 | 页级明细，点进去/按需查询才生成                                   | 按需           |

**两条实用规则**

- **默认只输出"有 gap 的文件"明细**。1000 份里 950 份全绿，那 950 份不进明细，报告从 1000 行降到 50 行。
- **对外只交付两个东西**：一份小的总报告（10 KB 级）+ 一份明细 CSV（可筛选）。**绝不交付包含 10 万行页级明细的单一巨型文档。**

### 4.8 分布式与部署管理模块

#### 4.8.1 控制面 / 数据面分离

| 面   | 状态               | 部署  | 扩展方式 |
| --- | ---------------- | --- | ---- |
| 控制面 | 有状态（任务状态机、预算、审计） | 主备  | 垂直   |
| 数据面 | 无状态（worker）      | 多副本 | 水平   |

#### 4.8.2 任务分发

- 队列：NATS / Redis / RabbitMQ（择一）
- 消息体：`(doc_id, page_range, engine, params, rulepack_hash)`
- 幂等键：`hash(文件) + 页范围 + 引擎 + 参数 + 规则包版本`
  > V2.1 变更：幂等键第二项由"页码"改为"页范围"，与批级并行对齐。
- 背压：队列长度触发降速，不打爆 GPU
  |   |   |
  | - | - |
- 亲和性：任务带 `resource_hint: cpu|gpu` 与 `doc_affinity_key`，调度器保证同一文档的所有批落到同一节点

#### 4.8.3 节点管理

- 注册/注销、心跳、状态与负载监控
- 故障自动识别与隔离
- 任务失败自动转移，死信队列
- 节点启动时校验插件依赖完整性（含 OCR 运行时的外部二进制与模型）

#### 4.8.4 私有化与国产化

- 完全离线，无外部依赖
- 数据不出域
- **OCR 模型与运行时随安装包分发**，首次启动不联网
- 国产化：麒麟/统信 OS、ARM 架构、达梦/人大金仓 DB 适配（P2）
- 见 R10：外部二进制在目标平台可能缺预编译包，需提前验证

#### 4.8.5 长进程稳定性与续跑

**本产品的典型任务是"1000 份文件、数小时"。这不是一个请求，是一个长进程。** 核心设计目标一句话：

> **worker 随时可以被杀掉，换一个 worker 接着做，结果不变。**

**落盘分层（不能都放一处）**

| 内容                                       | 存哪             | 丢了怎么办          |
| ---------------------------------------- | -------------- | -------------- |
| 任务状态、PageProfile、PageReport、PageGap、动作记录 | **PostgreSQL** | 不可丢。这是恢复的唯一依据  |
| 页产物（markdown + text_items）、临时增强 PDF、映射表  | **对象存储**       | 不可丢。重算需几十毫秒到几秒 |
| 渲染图、纠偏中间图                                | **本地临时盘**      | 可丢，重启清空        |
| 队列消息、worker 心跳                           | **Redis**      | 可丢，能从 PG 重建    |

> **规则：丢了要重算十秒以上的内容进对象存储；丢了只损失一点时间的进本地盘。** 临时文件放网络盘会导致性能骤降，明确禁止。

**续跑粒度必须按批，不能按文件**

200 页文件跑到第 180 页崩溃，按文件续跑要重做 200 页；按批（32 页）续跑最多损失一批。

- **每批完成即一个事务边界**：产物写入对象存储 + 状态更新进 PG，两者都成功才算这批结束。
- **写入顺序强制：先写内容，再写索引。** 反过来会出现"索引里有、内容找不到"的幽灵记录，续跑时误判为已完成然后读不到东西。

**三类中断分别处理**

| 中断   | 典型原因            | 处理                                  |
| ---- | --------------- | ----------------------------------- |
| 进程崩溃 | OOM、栈溢出、插件子进程崩溃 | 心跳超时检测 → 任务重新入队 → 从最后完成的批继续         |
| 单批异常 | 某份文件让解析器直接崩溃    | 捕获 → 该批标失败、写 `PageGap` → **不影响其他批** |
| 整体停机 | 手动重启、断电         | worker 全部无状态 → 控制面从 PG 恢复未完成任务      |

**必须用进程池，不能用线程池**

解析器是 Rust 扩展，**一旦段错误会直接杀掉整个 Python 进程，`try/except` 捕获不到**。

|       | 进程池（采用）                | 线程池（禁止）          |
| ----- | ---------------------- | ---------------- |
| 单个坏文件 | 子进程死，主进程记录并续跑该批        | 整个进程退出，任务卡死且无法恢复 |
| 代价    | 每进程需加载一次插件，内存开销大       | —                |
| 缓解    | 进程池内每个进程连续处理多个批，摊薄加载成本 | —                |

> 同一条理由也解释了为什么解析器必须独立进程（2.1）：**不是为分布式，是为故障隔离。**

**心跳按"进展"判定，不按"耗时"判定**

- 慢但仍在运行的批**不能被杀**，否则永远跑不完。
- 只有连续 **60 s 无心跳**才判死亡。
- 超时判定看"这一批最后处理到第几页有没有推进"，而不是"这一批跑了多久"。

#### 4.8.6 资源预检与配额

**必须分清两种预检，混在一起设计就会出问题。**

**A. 资源预检（准入闸门）—— 回答"现在还能开多少并发"**

| 检查             | 阈值                    | 不满足时               |
| -------------- | --------------------- | ------------------ |
| 可用内存           | < 总内存 20%             | 不取新任务，等待释放         |
| 临时盘可用空间        | < max(总容量 20%, 20 GB) | 不接新批               |
| CPU 负载（1 分钟均值） | > 核数 × 0.9            | 降低取任务速率，不新增 worker |

产出是"当前还能跑几个批"，而不是"内存够不够"。**它防的是把自己打满。**

**B. 文件体检 —— 回答"这个文件结构是否安全"**

见 4.1.8。两层分开的价值在于：**"内存不足"和"文件有毒"处理方式完全不同**，前者要限流，后者要拒收。现实中大部分崩溃属于后者。

**C. 运行中守卫（预检看得到"现在有多少内存"，看不到"这一批要吃多少"）**

| 层      | 时机         | 做什么                                                            |
| ------ | ---------- | -------------------------------------------------------------- |
| 准入     | 取任务前       | 见 A                                                            |
| **估算** | 取到批之后、开始之前 | 按 `页数 × 1.2 MB` 估算（4.3.7），超阈值**自动降批**                          |
| **守卫** | 运行中        | 给子进程设内存上限（Linux cgroup/rlimit，Windows Job Object），超限杀子进程而非杀主进程 |

**自动降批的退避链**

```
连续 3 个批因内存失败 → 批大小减半（32 → 16 → 8）
降到 8 仍失败 → 停止该任务并告警，不再重试
```

**启动自检 + 用户确认**

启动时跑一次自检，算出一页"部署建议"，用户可确认或修改：

| 节点规格    | worker 进程数 | 批大小  | 单进程内存上限 | 临时盘预留  |
| ------- | ---------- | ---- | ------- | ------ |
| 8C16G   | 6–8        | 16 页 | 1 GB    | 20 GB  |
| 16C64G  | 12–16      | 32 页 | 1.5 GB  | 50 GB  |
| 32C128G | 24–32      | 50 页 | 2 GB    | 100 GB |

**修改后必须做可行性校验**：填了 32 个 worker 但内存只够 12 个时，直接告警"当前配置预期会 OOM，建议改为 12"并降级，**不允许改完偷偷崩**。

#### 4.8.7 存储抽象与可替换性

三类存储的可替换性完全不同，一刀切会踩坑：

| 类型   | 例子                              | 可替换性  | 关键问题                          |
| ---- | ------------------------------- | ----- | ----------------------------- |
| 对象存储 | MinIO / S3 / OSS / 本地盘          | **高** | 接口就是 put/get/list/delete，几乎无损 |
| 队列   | Redis Streams / NATS / RabbitMQ | **中** | 至少一次 vs 精确一次、延迟消息、死信语义差异大     |
| 关系库  | PostgreSQL / MySQL / 达梦         | **低** | 事务、JSON、索引、窗口函数差异大            |

**对象存储：做抽象，值得做**

```
put(key, bytes) -> etag
get(key) -> bytes
exists(key) -> bool
delete(key)
list(prefix) -> iterator
```

**必须提供本地文件系统实现**——单机部署、开发调试、小客户都用它。

**队列：做抽象，但限制能力**

只依赖最小语义：**至少一次投递 + 手动确认 + 死信**。

- **禁止使用延迟消息与优先级队列**：这两项跨实现差异最大，用了就锁死在某个实现上。
- 需要延迟投递就在应用层做：消息带 `visible_at` 时间戳，消费方跳过未到期的。任何队列都能实现。

**关系库：P0 不做运行时切换，改限制 SQL 方言**

诚实结论：关系库的运行时切换成本会失控（PG 的 jsonb 运算符与 MySQL 完全不同，这是最容易埋雷的地方）。

P0 能做到的是**从第一天遵守标准 SQL 子集约束**：

| 约束                               | 原因                         |
| -------------------------------- | -------------------------- |
| 不用存储过程、不用触发器                     | 各库实现差异最大                   |
| JSON 字段只做整体存取，**禁止数据库端 JSON 查询** | jsonb / json_extract 语法不兼容 |
| 分页只用 `limit/offset`              | 避免方言差异                     |
| 时间统一存 UTC 毫秒整数，不用 `date` 类型      | 时区与精度差异                    |
| 不用自增序列做业务主键                      | 见下条铁律                      |

**一条零成本、必须现在就遵守的铁律**

> **页产物与文档的主键必须是内容哈希，不能是自增 ID。**

内容寻址的 key 换存储时不变，搬数据安全；用自增 ID 再映射到对象 key，换底座时整个映射会错乱。

**分档落地**

| 阶段     | 做什么                                                      |
| ------ | -------------------------------------------------------- |
| **P0** | 对象存储抽象（MinIO + 本地盘两实现）；关系库用标准 SQL 子集（不抽象）；队列用 Redis（不抽象） |
| P1     | 队列抽象（加 NATS）                                             |
| P2     | 关系库适配（达梦 / 人大金仓）：改 DDL + 改查询，仍不做运行时切换                    |

> P0 不做全套的理由：换底座的真实需求来自政企信创客户，那是 P2 才见的场景；在没有第二个真实实现之前设计的抽象层，大概率是错的。

#### 4.8.8 交付形态与单机 / 多机一致性

**形态定义：CLI 是唯一入口，Web 由 CLI 拉起，二者同属一个进程。**

```
$ dataagent up

  自检：8C16G / 可用内存 11.2G / 临时盘 120G
  建议配置：worker=8，批大小=16，单进程上限 1GB   [已采纳]
  启动 Redis / PostgreSQL / MinIO ... 就绪
  启动 worker (8) ... 就绪
  启动 API :8080

  已就绪 → http://127.0.0.1:8080
```

用户体感是"一个本地应用"，而不是"一个 Web 服务"。这与 Ollama / n8n / Jupyter 的做法一致。

**三种交付形态（递进关系，不是并列选项）**

| 形态                     | 入口                                       | 适用              | 多机迁移                                |
| ---------------------- | ---------------------------------------- | --------------- | ----------------------------------- |
| **Docker Compose**（主推） | `docker compose up -d`                   | 绝大多数客户          | 同一份 compose 换外部 DB/Redis/MinIO 地址即可 |
| **pipx 单机**            | `pipx install dataagent && dataagent up` | 无 Docker 的个人/开发 | 需切换后端实现                             |
| **离线包**                | tar 包含镜像 + wheel + 模型 + 字体               | 政企无外网           | 同 Compose                           |

**离线包是政企硬需求**：镜像 tar、离线 wheel、OCR 模型、字体包一次打全，安装脚本只做 `docker load` + `compose up`。

**单机 → 多机，只有一个前提：单机版从一开始就保留进程边界，不允许出现"单机专用代码"。**

| 维度       | 正确做法               | 错误做法（永远迁不动）                     |
| -------- | ------------------ | ------------------------------- |
| 任务分配     | worker 从队列取，状态在 PG | 主进程 `multiprocessing.Pool` 直接派活 |
| 产物存放     | 对象存储接口（本地盘是一种实现）   | 直接写 `./output/`                 |
| 进度查询     | 查 PG 状态表           | 查内存里的 future / 线程字典             |
| worker 数 | 配置项                | 写死 `cpu_count()`                |

**只要四条都守住，迁移到多机 = 改配置 + 多起几个 worker 容器 + 前面挂反向代理**，API 与 worker 本来就是无状态的。

**因此"单机版"的定义是：用同一套代码，把后端实例起在本机。不是另一套代码。**

**五条必须从第一天守住的约束**

1. **API 无状态**：所有状态进 PG，API 进程可随意重启、随意多起。
2. **worker 无状态**：任务归属靠队列，worker 死了换一个接着干。
3. **Web 只做控制面**：查进度读 PG，不读 worker 内存；上传文件先进对象存储，不进 API 进程内存。
4. **配置只有一份**：`.env` / `config.yaml`，单机多机同一 schema，差别只是值。**不做两套配置格式。**
5. **资源自检跑在启动时**（4.8.6），建议值由机器规格推出，用户确认后写入运行配置。

**P0 的界面范围（前端后置时不失演示能力）**

- 一个只读状态页 `/status`：服务端渲染 + 定时刷新，**不引入构建链**
- 内容：任务列表、进度、gap 摘要、队列深度、worker 存活数
- **消费的是 P2 正式前端要用的同一批 API**，P2 只替换视图层，不改后端

**无头环境必须有出路**：`dataagent status / logs -f / plugin list`，SSH 进服务器是私有化部署的真实场景。

**必须提供的子命令 `doctor`**

检查 Docker 版本、端口占用、磁盘余量、内存、模型文件完整性、字体是否安装、外部二进制是否存在。

> **私有化部署 80% 的失败是环境问题，不是代码问题。** 一个 `doctor` 能省掉大量支持工单。

**不做的事**

1. 不做桌面安装包（Tauri / Electron 套壳）——P0 收益低，等有明确需求再说。
2. 不做"单机精简版"——一旦出现第二套代码路径，多机版就变成没人测过的分支。
3. 不让 Web 承担计算——上传、解析、抽取全在后端。
4. P0 不做多租户与集群管理台。

### 4.9 可观测与运营监控模块

#### 4.9.1 全链路追踪

每个任务可追溯：接入 → 一级判定 → 二级分类 → 路由决策（含 reason 与 profile_snapshot）→ 解析（插件/参数/耗时）→ L1/L2/L3 指标 → 兜底档位 → 归因 → 修复动作 → 合并 → 输出。

**Trace 字段要求**：`task_id, doc_id, page_no, stage, engine, params_hash, duration_ms, cost, verdict, tier, attribution, action`。

#### 4.9.2 核心指标看板

| 指标         | 定义                                  |
| ---------- | ----------------------------------- |
| 处理量        | 页/日、文档/日                            |
| STP 率      | 一次通过文档数 / 总文档数                      |
| 误放率        | 人工复核不合格但系统判 pass 的比例                |
| 人工升级率      | 进入待办队列的文档数 / 总文档数                   |
| 平均单页成本     | 总成本 / 总页数                           |
| 失败分布       | 按失败分类法统计                            |
| **档位分布**   | T0/T1/T2/T3 各占页数比例（T3 占比是成本预警的核心指标） |
| **T1 命中率** | 走 T1 且修复成功的页数 / 走 T1 的页数            |
| p50/p95 时延 | 端到端                                 |
| 复杂页占比      | `is_complex` 页 / 总页数                |

#### 4.9.3 告警

- STP 率跌破阈值
- 误放率超阈值
- 单页成本异常上涨
- **T3 占比异常上涨**（意味着自建后处理覆盖不足）
- 队列积压
- 节点离线
- 归因分布漂移（某类失败突增）

#### 4.9.4 系统管理

- 用户权限分级
- 系统参数配置
- 插件管理与版本控制（能力索引、启停、版本锁定，见 5.5）
- 审计日志查询与导出

## 五、关键设计约束

### 5.1 插件契约（manifest）

```yaml
manifest:
  id: engine.pdf
  name: PDF 解析与分类插件
  version: 1.0.0
  api_version: 1
  kind: engine                # engine | validator | extractor | connector | exporter
  provides:                   # V2.2：能力签名结构化，不是字符串标签
    - capability: pdf.classify
      input:  { schema: doc.bytes }
      output: { schema: pdf.classification.v1 }
      latency: { p50_ms: 25, unit: document }
    - capability: pdf.text.extract
      input:  { schema: doc.bytes, params: page_range }
      output: { schema: page.artifact.v1 }
      latency: { p50_ms: 16, unit: page }
  cost_model:
    unit: page
    classify_ms_p50: 25       # 文档级分类，非页级
    cpu_ms_p50: 16            # 页级抽取
    cpu_ms_p95: 40
    gpu_ms: 0
    memory_mb: 200
  determinism: deterministic  # deterministic | stochastic | model
  concurrency: reentrant      # reentrant | exclusive | thread_unsafe
  trust: builtin              # builtin | signed | unsigned
  sandbox: none               # none | subprocess | container | remote
  limits:
    max_page_size_mb: 50
    timeout_s: 30
  batching:                   # V2.1 新增：声明批量能力，调度器据此成批
    supported: true
    default_batch_pages: 32
    max_batch_pages: 50
    batch_affinity: document  # 同一文档的批必须同机
  optional_deps:              # V2.1 新增：可选运行时依赖，离线部署据此校验
    - name: pdfium
      required_when: [pdf.ocr]
    - name: onnxruntime
      required_when: [pdf.ocr]
  compatibility:
    requires: []              # 内核/API 版本、Python 版本、外部二进制最低版本
    conflicts: []
```

**V2.2 新增字段的用途（每个字段都有明确消费者，不是凑数）**

| 字段            | 取值                                       | 消费者与用途                                                                                        |
| ------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| `provides`    | 结构化签名（含输入输出 schema 与延迟）                  | 注册表做能力索引；调度器做能力匹配与成本排序                                                                        |
| `determinism` | `deterministic / stochastic / model`     | **决定能否重试、能否缓存。** 只有 `deterministic` 允许启用结果缓存（缓存键 = 内容哈希 + 参数哈希 + `id@version`），且调度器据此拒绝 T2 重跑 |
| `concurrency` | `reentrant / exclusive / thread_unsafe`  | 决定并发调度：`exclusive` 的插件在同一时刻只允许一个实例运行                                                          |
| `trust`       | `builtin / signed / unsigned`            | 决定沙箱强度与能否上线（见 5.5）                                                                            |
| `sandbox`     | `none / subprocess / container / remote` | 决定调用面形态（见 5.5）                                                                                |
| `cost_model`  | 含 `memory_mb`                            | 参与 4.8.6 的批大小与 worker 数计算                                                                     |

> **`determinism` 是最关键的字段。** 它同时解锁两件事：**缓存**（仅确定性插件可缓存）与**重试合法性判定**（4.5.8）。缺少该字段就开缓存，迟早读到脏产物。

**验收要求**：

1. 任何插件不符合该契约，不得上线。
2. **`provides[].capability` 中存在 `*.classify` 的，其 classify 能力必须能在不产内容的前提下完成判定**（不得内部偷偷做全量抽取再返回分类结果）。
3. 声明 `batching.supported: true` 的插件，必须支持一次调用传入多页，且保持调用方给定的顺序。
4. **`trust: unsigned` 的插件必须声明 `sandbox` 非 `none`**，且默认禁用，需显式开启。
5. **`determinism` 字段缺失或声明为 `stochastic / model` 的插件，不得启用结果缓存**，且每次调用都计入成本预算。

### 5.2 数据模型

| 实体                       | 关键字段                                                                                     | 说明                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `Task`                   | task_id, spec, state, budget, **resume_point**                                           | 一次任务；`resume_point` = 最后完成的批（4.8.5）                                                            |
| `Document`               | doc_id(hash), family, page_count, profile, **health**                                    | 一个文件；`family` 为一级判定结果，`health` 为 4.1.8 体检三态                                                    |
| **`PageProfile`**        | doc_id, page_no, class, layout, signals, quality                                         | **V2.1 新增**：页面画像，分两次写入（路由段 / 质量段）                                                              |
| `PageArtifact`           | doc_id, page_no, engine, params_hash, content, scores, tier                              | 不可变                                                                                            |
| `PageReport`             | 指标 + verdict + **defects[]**                                                             | 质检结果；缺陷清单见 4.5.7                                                                               |
| **`Defect`**             | defect_id, doc_id, page_no, **code, location, evidence, severity**, `raw_reason`         | **V2.2 新增**：可独立查询与统计；无 `location` 不得入库。`code = plugin_reason_unknown` 时 `raw_reason` 必填（4.5.7） |
| **`PageGap`**            | doc_id, page_no, defect_codes[], tried_operators[], recommended_tier, fallback_used      | **V2.2 新增**：复杂页收口记录（4.5.10）                                                                    |
| `DocReport`              | 聚合指标 + 诊断                                                                                | 文档级                                                                                            |
| `RulePack`               | id, version, content, status                                                             | 策略数据                                                                                           |
| `Action`                 | id, page, type, params, tier, result, **changed**                                        | 修复动作；`changed` 为停机依据（4.5.9）                                                                    |
| **`PluginRegistration`** | plugin_id, version, kind, provides[], determinism, trust, sandbox, enabled, installed_at | **V2.2 新增**：插件注册表条目（5.5）                                                                       |

**关系**：`Document 1—N PageProfile 1—N PageArtifact`。同一页可有多个 artifact（不同引擎/参数），但同一幂等键只对应一个。`PageReport 1—N Defect`，`PageGap` 由未修复的 `Defect` 聚合而来。

**主键铁律（V2.2 新增，零成本但决定三年后能否换底座）**

> **文档与页产物的主键必须是内容哈希（SHA-256），不得使用自增 ID。**

理由：内容寻址的 key 在更换存储后端时不变，搬数据安全；若用自增 ID 再映射到对象 key，换底座时整个映射会错乱（4.8.7）。

### 5.3 状态机

| 状态            | 进入条件            | 动作                         | 出口                                                       |
| ------------- | --------------- | -------------------------- | -------------------------------------------------------- |
| `RECEIVED`    | 接入完成            | 完整性检测、建任务                  | 通过→`SNIFFED`；失败→`REJECTED`                               |
| `REJECTED`    | 边界处理未通过         | 写诊断码、入待确认队列                | 人工处理                                                     |
| `SNIFFED`     | 一级判定完成          | 按家族派发                      | pdf→`CLASSIFIED`；其他→`ROUTED`                             |
| `CLASSIFIED`  | `detect_pdf` 完成 | 写 PageProfile 前两段、逐页分配链路   | `ROUTED`                                                 |
| `ROUTED`      | 链路确定            | 分批、入队                      | `PARSING`                                                |
| `PARSING`     | worker 取到任务     | 批量解析                       | `PARSED`                                                 |
| `PARSED`      | artifact 落库     | 算 L1、写 PageProfile 后两段、判档位 | `POSTPROCESS`（T1）/ `L1_CHECK`（T0）/ `REPAIRING`（T2/T3）    |
| `POSTPROCESS` | 档位 = T1         | 表格 cell 重建、页眉页脚剔除、跨页段重排    | `L1_CHECK`                                               |
| `L1_CHECK`    | 指标算完            | 硬门控                        | pass→`L2_CHECK`；fail→`ATTRIBUTED`                        |
| `L2_CHECK`    | 抽样命中            | 往返/跨引擎/VLM                 | pass→`MERGED`；fail→`ATTRIBUTED`                          |
| `ATTRIBUTED`  | 归因完成            | 选动作、判档                     | 判为 T1→`POSTPROCESS`；判为 T2/T3→`REPAIRING`；无法判→`ESCALATED` |
| `REPAIRING`   | 动作确定且为 T2/T3    | 执行重跑 / 换引擎                 | `PARSING`（同页/同批）                                         |
| `MERGED`      | 页级通过            | 组装                         | `L3_CHECK`                                               |
| `L3_CHECK`    | 文档级校验           | 勾稽/连续性                     | pass→`PUBLISHED`；fail→局部回退                               |
| `PUBLISHED`   | 输出完成            | 通知                         | 终态                                                       |
| `ESCALATED`   | 预算耗尽            | 诊断卡                        | 人工                                                       |

> **`POSTPROCESS` 是 V2.1 新增状态**：T1 后处理必须作为独立可观测状态存在，否则无法统计"T1 命中率"与"T1 耗时"，也就无法判断自建后处理是否做够了。

> **V2.2 修正**：原表 `ATTRIBUTED` 只有 `REPAIRING` / `ESCALATED` 两个出口。但 L1 fail 后若归因为 `header_footer_leak`、`table_structure_broken` 等**可纯后处理修复**的缺陷，判档会落到 T1——此时没有合法出口，实现只能被迫重跑解析，而这对确定性函数毫无意义。V2.2 补入 `POSTPROCESS` 出口。**判定规则：T1 动作改的是已有 artifact，绝不回到 `PARSING`。**

**中断与续跑（V2.2 新增，不改变状态定义）**

| 场景        | 规则                                                     |
| --------- | ------------------------------------------------------ |
| worker 崩溃 | 任务状态保持原状态不变，由控制面重新入队；恢复时从 `Task.resume_point` 指向的批之后继续 |
| 批级回滚      | 只有"产物已写入对象存储 **且** 状态已提交"的批才算完成；只写了一半的批整体重做            |
| 恢复后的状态判定  | **状态机不新增状态**。恢复 = 重新执行当前状态的动作，因此每个状态的动作必须幂等            |
| 禁止        | 不允许出现在"状态已变为 `PARSED` 但产物读不到"的情况（写入顺序见 4.8.5）          |

### 5.5 插件注册表与治理（V2.2 新增）

**先把三件事拆开，它们经常被混为一谈：**

|                  | 是什么                                             | 什么时候需要            | 本产品结论             |
| ---------------- | ----------------------------------------------- | ----------------- | ----------------- |
| **注册表 Registry** | 控制面。谁存在、什么版本、提供什么能力、依赖什么、能否启用。只做元数据查询，**不参与调用** | 一开始就需要            | **P0 必做**         |
| **网关 Gateway**   | 数据面。跨进程/跨机调用代理，管鉴权、配额、熔断、灰度                     | **只有插件不在同一进程才需要** | **P0 不做**（见下）     |
| **MCP Server**   | 协议面。把能力暴露成 LLM 可调用的工具                           | 对外输出时             | **P2 做出口，不做内部调用** |

**为什么 P0 不做独立网关**

本产品绝大多数插件调用是**同进程高频纯函数**（每页一次校验、每批一次抽取）。加一层网关意味着每次调用多一次序列化 + 一次 RPC：

| 传输方式          | 单页往返     | 200 页合计   | 对比 L1 计算本身（< 1 ms/页） |
| ------------- | -------- | --------- | -------------------- |
| 共享内存 + pickle | 1–3 ms   | 0.2–0.6 s | 贵 2–3 倍              |
| 管道 + JSON     | 15–25 ms | 3–5 s     | 贵 20 倍               |

**这会直接抵消 10–25 ms/页 省下的成本**，且换不来任何需要的能力。

**插件按热度分两类，形态不同**

|    | 热路径                                  | 冷路径                                       |
| -- | ------------------------------------ | ----------------------------------------- |
| 例子 | `engine.pdf`、`validator.l1`、T1 后处理算子 | OCR 引擎、外部增强器、connector、exporter、extractor |
| 频次 | 每页 / 每批                              | 每文件 / 每任务                                 |
| 信任 | 内置                                   | 第三方 / 客户自写                                |
| 形态 | **同进程直接调用**                          | **子进程沙箱 + 调用面**                           |

一个系统里两种形态并存是正常的，不是不一致。

**注册表必须提供的能力**

| 能力      | 要求                                                                                               | 阶段             |
| ------- | ------------------------------------------------------------------------------------------------ | -------------- |
| 能力索引    | 按 `provides[].capability` 查询实现方，返回候选列表（含版本、成本、信任级）                                               | P0             |
| 启用 / 禁用 | 运行时开关，不重启进程                                                                                      | P0             |
| 版本锁定    | 任务可锁定插件版本，保证历史可复现                                                                                | P0             |
| 依赖校验    | 启动时校验 `requires` 与 `optional_deps`，缺失则拒绝加载该插件并告警                                                 | P0             |
| 兼容性校验   | `api_version` 语义化版本比对，不兼容直接拒载，**不允许运行时崩**                                                        | P0             |
| 多实现选择   | 显式优先级 + 任务规格可指定；默认选"满足约束的最高优先级"                                                                  | P0 定规则 / P1 实现 |
| 调用观测    | 每次调用记 span：`plugin_id@version, capability, duration, bytes_in/out, cache_hit, cache_miss_reason` | P1             |
| 灰度与回归   | 按比例分流到新版本，对比 STP 率与 T3 占比                                                                        | P2             |

**两条禁止的隐式行为**

1. **禁止"后加载覆盖先加载"。** 同名能力的多实现必须由显式优先级决定，隐式覆盖会造成"换台机器行为就变了"的排查地狱。
2. **禁止插件之间直接互相调用。** 必须经调度器，否则依赖图不可控、无法审计、预算无法集中扣减（2.6）。

**信任分级**

| 级别         | 来源          | 允许的能力         | 沙箱要求                            |
| ---------- | ----------- | ------------- | ------------------------------- |
| `builtin`  | 随产品发布       | 全部            | 可 `none`                        |
| `signed`   | 第三方，有签名与校验和 | 除 connector 外 | **必须** `subprocess` 及以上         |
| `unsigned` | 客户自写 / 来源不明 | 默认禁用，需显式开启    | **必须** `container`，禁网、只读输入、资源限额 |

**沙箱边界（`signed` 及以上通用）**

- 插件只能拿到声明的输入，不能读全局上下文或任务全局状态
- **默认禁网**；只有 `connector` 类型允许出网，且走域名白名单
- 只读挂载输入目录，只写自己命名空间下的输出
- 子进程内存与时长上限由 4.8.6 的资源守卫统一施加

**"企业级"的准确定义（用于阻止无意义的模块堆砌）**

> 企业级不是"有一个网关"，而是**可审计、可回滚、可灰度、故障可隔离**。这四条靠注册表 + span + 版本锁定就能实现；独立网关只在特定条件下才是企业级，否则是负债。

**独立网关的触发条件（满足两条以上才做，P2 评估）**

1. 多租户按配额限流
2. 插件由第三方提供且不可信（对应 `trust: unsigned` 规模化）
3. 插件需独立扩缩容（GPU 池）
4. 跨语言 / 跨机器

**MCP 的位置：出口，不是入口**

- **内部不使用 MCP**。MCP 是"LLM 与工具"的协议，本产品内部是"代码与代码"，用 MCP 包内部高频调用 = 每次 JSON-RPC + 描述注入，纯亏。
- **P2 对外暴露一个 MCP Server**，把"整份数据处理能力"作为一个工具供其他 Agent 调用（提交任务、查询进度、取结果）。这才是 MCP 的正确用途。
- 个性化字段提取的模型兜底（4.6.6 第③层）若需经 MCP 暴露，**输出必须过 JSON Schema 校验**。

**四个必须避免的反模式**

1. 插件里做路由决策 —— 路由必须确定性（4.2）
2. 插件之间直接互相调用 —— 见上
3. 插件自己重试 —— 预算失控，违反停机条件（4.5.9）
4. 用插件机制实现"配置" —— 配置是数据不是代码；阈值做成插件会导致无法统一标定

## 六、非功能需求

### 6.1 性能

| 指标            | 目标                              | 定义与测量                                        |
| ------------- | ------------------------------- | -------------------------------------------- |
| 单节点吞吐         | ≥ **30 万页/日**（16C64G）           | 前提：简单页 ≥ 80%，端到端 ≤ **150ms/页**；连续 1 小时压测取稳定值 |
| 简单 PDF 单页     | p50 ≤ **120ms**，p95 ≤ **250ms** | 端到端（含分类、L1 校验与落库）                            |
| PDF 分类        | p50 ≤ 30ms / 文档                 | `detect_pdf` 单次调用                            |
| PDF 页级抽取      | p50 ≤ 16ms / 页，p95 ≤ 40ms / 页   | 批内摊算；批大小 ≥ 20                                |
| 10 万行 CSV     | ≤ 5s                            | 含编码嗅探与类型推断                                   |
| 单任务规则校验       | ≤ 100ms                         | 不含 IO                                        |
| 调度响应          | ≤ 1s                            | 从入队到 worker 开始                               |
| 集群扩展          | 10 节点吞吐提升 ≥ 70%                 | 文档级分片；控制面不成为瓶颈                               |
| **单进程峰值内存**   | **≤ 50 MB**                     | 批大小 32 页条件下测 RSS（依据 4.3.7）                   |
| **中断后续跑**     | 恢复耗时 ≤ 30 s，已完成的批 0 重做          | 强杀 worker 后恢复（4.8.5）                         |
| **单机 → 多机迁移** | 只改配置，不改代码，不重编译                  | 同一镜像切换后端地址（4.8.8）                            |
| 启动自检耗时        | ≤ 3 s                           | 含资源探测与依赖校验                                   |

**吞吐核算**：30 万页/日 = 3.5 页/秒。16 核按 16ms/页 理论可达 1000 页/秒，实际瓶颈在 L2 抽样、IO 与落库。目标值留有充足余量，若实际未达标，说明问题不在解析插件。

## 九、商业价值论证

### 9.1 市场与客户

- **市场**：智能文档处理（IDP），全球规模数十亿美元级，年增速 20%+。
- **客户画像**：银行、保险、券商、审计、律所、政府档案、大型企业财务共享中心。

### 9.3 差异化与护城河

**差异化（客户能感知的）：**

1. **成本**：80% 走 CPU，加权单页成本约为全量 OCR 的 **1/10 以下**。
2. **边界清晰**：明确告知哪些页没把握，而不是假装全部成功。
3. **规则自助**：业务人员改规则，不用等研发。
4. **私有化**：离线、数据不出域。

**护城河（真正的壁垒）：**

- 垂类评测集（财报 / 法规 / 合同）
- 交付模板库（RulePack 复用）
- **T1 后处理的场景积累**（页眉页脚模式、跨页表续接规则）—— 这部分是最难被复制的

> 注意：**"插件化"不是护城河**，它是架构选择。对外传播时，讲"成本、边界、自助、私有化"，不要讲插件。

### 9.4 单位经济模型（示例值，需实测标定）

| 页型                      | 占比   | 单页耗时      | 单页成本            |
| ----------------------- | ---- | --------- | --------------- |
| 简单（CPU 抽取 + 分类摊销）       | 80%  | ~30ms     | ¥0.0005–0.001   |
| 中等（CPU + T1 后处理 + 抽样校验） | 15%  | ~120ms    | ¥0.003–0.008    |
| 复杂（OCR/VLM）             | 5%   | 2–5s（GPU） | ¥0.1–0.3        |

**结论**：加权成本约为全量 OCR 的 1/10–1/25。这是产品最硬的价值主张。

## 附录 B：指标公式

```
CER        = (S + D + I) / N
TEDS       = 1 - TED(预测表, 参考表) / max(节点数)
reading_order_score = 1 - 逆序对数 / 总对数
fidelity   = w1·(1-CER) + w2·TEDS + w3·semantic_match + w4·layout_iou
STP        = 一次通过文档数 / 总文档数
误放率      = 人工判不合格且系统判 pass 的样本数 / 人工判不合格样本数
加权单页成本 = Σ(页型占比 × 单页成本)

glyph_coverage  = (cmap_gaps.codes - cmap_gaps.unmapped) / cmap_gaps.codes
cid_unmapped_ratio = cmap_gaps.unmapped / cmap_gaps.codes
char_density    = 抽取字符数 / 文本区域面积

extract_quality = f(glyph_coverage, char_density_norm, empty_region_ratio,
                    warning_count, bbox_coverage)
                  权重与归一化参数由黄金集拟合（4.4.7）

T1 命中率 = T1 修复成功页数 / T1 页数
T3 占比   = 走 T3 的页数 / 总页数          （成本预警核心指标）

# [V2.2 新增]
单进程峰值内存 ≈ 批页数 × 1.2 MB × 1.3                  （4.3.7）
worker_进程数  = min(核数 × 1.25, 可用内存 / 单进程上限, 32)   （4.3.8）
聚包数        = ⌈跨文档失败页总数 / 包大小⌉              （4.5.10）
缺口页占比    = gap 页数 / 总页数                        （4.7.4 交付等级依据）
T1 覆盖率     = T1 修复成功页数 / 全部 fail 页数         （T3 占比的对偶指标）
归因模型调用  ≤ fail 页数 × 1.1                          （2.6 开销预算）
```

| 方式            | 单页往返      | 200 页     | 结论             |
| ------------- | --------- | --------- | -------------- |
| 共享内存 + pickle | 1–3 ms    | 0.2–0.6 s | 比 L1 计算贵 2–3 倍 |
| 管道 + JSON     | 15–25 ms  | 3–5 s     | 比 L1 计算贵 20 倍  |
| 仅传特征向量（2 KB）  | < 0.05 ms | < 0.01 s  | **可忽略，故判定可外置** |

### D.2 插件参数暴露面（决定"换参数"这条路可不可靠）

`engine.pdf` 实际可调的参数仅：

```
pages                    页范围（批级抽取用）
bold_from_weight         是否用字重推断粗体
bold_weight_threshold    字重阈值
model_directory          OCR 模型目录
offline                  离线模式
render_dpi               渲染分辨率
```

**表格检测模式、分栏阈值、阅读顺序策略均未暴露为参数。**

因此 4.5.8 的类别 ③（换参数）在设计上就不能作为主要手段。凡是声称"调个参数重跑就能修好表格/分栏"的方案，都是对该插件能力的误判。

### D.3 四类算子的实现参考

| 算子                            | 实现要点                                                                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `rebuild_table_cells`（后处理）    | 用 `text_items` 的 bbox 做行聚类（y 重叠 + 间隔阈值）→ 列聚类（x 重叠）→ 生成 `cells` 与合并单元格；不调用插件                                          |
| `strip_header_footer`（后处理）    | 取页面上/下 8% 区域内的 item，与相邻页同位置 item 做文本相似度比对，重复率 > 0.8 判为页眉页脚                                                           |
| `reorder_blocks`（后处理）         | 按 `columns` 数把页面横向分带，带内按 y 排序，带间按 x 排序；与插件给出的 `reading_order` 做最小编辑距离比较后择优                                           |
| `merge_cross_page_table`（后处理） | 相邻页表头列名相似度 + 列数一致 + 表体触页边界三条件同时满足才合并；合并后表头去重                                                                         |
| `extract_region`（换输入）         | 用 `extract_text_in_regions(path, page_regions)` 定点补抽，返回的 `RegionText` 自带 `needs_ocr`，可按区域粒度决定是否送 OCR，不必整页送           |
| `resegment_columns`（换输入）      | 按栏切分为多个子页区域，分别定点抽取后再拼接；**不要**改 `/Rotate`，分栏不是旋转                                                                      |
| `rotate_page`（换输入）            | 页面正但旋转 90° 时改 `/Rotate` 属性即可，插件会按旋转后坐标系输出，快且无损；**文本本身画歪（扫描倾斜几度）必须 render → 纠偏 → 走 OCR**，改 `/Rotate` 无效               |
| 裁边（换输入）                       | **改 `/CropBox`，不要裁像素**。插件坐标原点为"可见页框（CropBox ∩ MediaBox）左下角"，改 CropBox 后坐标系自动跟随，`extract_text_with_positions` 坐标仍正确   |
| 所有换输入类                        | 优先走 `*_bytes` 接口（`process_pdf_bytes` / `extract_pages_markdown_bytes` / `extract_text_in_regions_bytes`），内存直传，不落临时文件 |

### D.5 增强回路伪代码（供技术方案参考）

```python
def enhance(artifact, defects, budget):
    for d in defects:                       # 按 severity 降序
        if d.code in tried:                 # 同码唯一
            continue
        tried.add(d.code)
        op = MAP[d.code]                    # 映射表写死
        if op.tier == "T1":
            cost = 0
        elif not budget.consume(op.tier):
            return escalate(artifact, defects)

        r = op(artifact, d, ctx)
        if not r.changed:                   # 无变化 = 此路不通
            mark_dead_end(d.code)
            continue
        if improvement(artifact, r.candidate, d) < 0.05:
            continue                        # 有变化但无进展，丢弃候选
        artifact = r.candidate
        defects = recheck(artifact, d.scope) # 只复检相关范围
        if not defects:
            break
    if defects:
        return escalate_with_gap(artifact, defects)
    return artifact
```

### D.6 上游返回字段的三个坑（技术方案必读）

| 坑                                   | 事实                                                                                                                                                                                                                                                                             | 处理                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| **页码基准不统一**                         | `classify_pdf` 的 `pages_needing_ocr` 是 0-indexed；`extract_pages_markdown` 的 **入参 `pages` 是 0-indexed、返回的 `pages[].page` 也是 0-indexed**，但同一个返回对象里的 `pages_with_tables` / `pages_with_columns` / `pages_needing_ocr` 是 **1-indexed**；`detect_pdf` / `TextItem.page` 全部 1-indexed | 字段级转换，转换点只允许一处（4.3.3）。断言式单测固定：`pages=[k]` → `pages[0].page == k` 且 `k+1 in pages_with_tables` |
| **`confidence` 是文档级分类把握**           | 不反映页级抽取质量，且同文档所有页取值相同                                                                                                                                                                                                                                                          | 只写入 `class_confidence`；页级质量用自建 `extract_quality`（4.4.6）                                       |
| **`cmap_gaps` 在 `detect_pdf` 下恒为空** | 编码诊断必须抽取后才可得                                                                                                                                                                                                                                                                   | `signals.glyph_coverage` 与 `encoding_loss` 判定只能发生在解析之后（4.3.5 时序）                              |

**`ocr_reason` 是开放字符串集合，文档未给枚举。** 技术方案必须包含一次"原因码枚举"工作项：

1. 取 50–100 份真实样本（覆盖纯文字、扫描、双栏、表格、混合、损坏编码），全量跑 `detect_pdf` + `extract_pages_markdown`；
2. 收集两侧出现的全部 `ocr_reason` / `reasons[]` 字符串，去重成表，标注每条的语义与对应缺陷码；
3. 该表作为配置文件的初始内容（4.5.7 规则 1），并记录采集时的插件版本；
4. 上游升级后重跑同一脚本，diff 出新增项 → 决定是补映射还是留待 `plugin_reason_unknown` 观察。

> 工作量约半天，但它是"复用上游逐页归因"这件事能否落地的唯一路径。跳过这一步，4.5.7 的映射表就只能靠猜，而猜错的表现是：缺陷码归错、算子用错、报告写错原因，三者都不会报错。
